# 训练并行演进史：瓶颈如何从副本转移到布局与调度

> 范围：大模型训练的系统路线。年份为所引论文首次公开年份，会议年份另注；问题之间的联系是本文的分析，不表示论文之间均存在直接继承。不同路线长期并存。

## 起点：模型能放下，训练太慢

最容易分配的是独立样本：每张卡保存相同模型，各自前后向，再归约梯度。固定全局目标、随机性与数值条件时，DP可以保持与大batch参考计算相同的更新语义。吞吐收益来自分摊样本计算，不来自减少每个副本的模型状态。

规模扩大后，更新前必须拿到所有参与者的贡献。慢rank、梯度就绪顺序、网络与计算的重叠决定等待时间。DDP的bucket化把“一次反向之后才通信”改为“梯度逐步就绪时通信”，但过小bucket会增加启动次数，过大bucket会延迟首个通信。当前实现机制可查[PyTorch DDP设计文档](https://docs.pytorch.org/docs/stable/notes/ddp.html)，这里不把当前API的发布时间当作DP的起源。

**新问题不是简单的带宽不足。** 变长样本还会让各rank有效token数量不同；各自求均值再平均会改变目标。同步机制只能合并给它的数，不能纠正错误的分母。[DDP完整推演](推演_DDP梯度与通信时间线.md)同时展示这两个问题。

DP仍适合模型和训练状态能放下、单副本算子足够大的情况。并行越复杂越先进的说法在这里没有意义。

## 2018：沿模型深度分工，把小批次送入流水线

模型放不下时，按层切开具有自然边界。但如果一整个batch按stage串行通过，其余设备仍然闲置。GPipe将batch分成microbatch，使不同stage同时处理不同microbatch，并累积梯度后更新。[GPipe，2018](https://arxiv.org/abs/1811.06965)。

这种方法用调度换取设备重叠，却引入warmup、drain和激活保存。增加microbatch数量能够摊薄某些气泡，但也可能让单个GEMM变小、通信更碎；模型层耗时不均时，最慢stage仍支配速度。

另一条流水线路线关注持续运行与权重版本。PipeDream讨论流水中的权重一致性和weight stashing；其2018年预印本与SOSP 2019工作可结合作者仓库查阅。不能把所有1F1B排程都等同于异步权重更新：同步flush的1F1B也可以让整批microbatch使用同一组参数。[PipeDream论文](https://arxiv.org/abs/1806.03377)、[作者实现与版本说明](https://github.com/msr-fiddle/pipedream)。

[两阶段推演](推演_PP调度与激活峰值.md)给出一个有意简单的反例：GPipe与同步1F1B都耗时10个时槽，但激活峰值不同。调度改变内存，并不自动意味着减少这组条件下的气泡。

## 2019：单层也太大，进入算子内部切分

只按层切分无法解决单层容量，stage也未必足够多。Megatron-LM利用Transformer的矩阵结构，组合列切分与行切分，将中间分片保留在本地，在需要恢复全局结果的边界通信。[Megatron-LM，2019](https://arxiv.org/abs/1909.08053)。

这让单层参数与计算可以跨设备分摊。新增约束是更高频的同步和更小的本地算子：同一层可能每次前后向都要collective，TP跨慢网络扩展不一定划算。非线性的位置也限制切分，不能把任意两个矩阵乘之间的归约随意删掉。

[TP矩阵推演](推演_TP前向反向与Attention.md)把这些边界落实为数值：列切分后的激活如何对应行切分权重，前向部分和在哪里归约，反向输入梯度为什么还要归约。Attention则要同时区分token维、head维与head内部维度。

## 2019：不是所有状态都必须在每个DP副本重复

Adam训练除了模型权重还保存梯度和优化器状态。ZeRO按阶段消除优化器状态、梯度、参数的冗余，使DP组中的设备共同拥有训练状态。[ZeRO，2019](https://arxiv.org/abs/1910.02054)。FSDP是相关分片执行路线，具体参数展开、预取、重分片由实现和配置决定，不能仅用一个stage编号概括全部行为。

收益来自减少持久副本；新增成本来自使用前收集参数、反向后分发梯度，以及执行中的临时完整参数。更多设备可能降低常驻状态，却不同比例降低当前layer的展开峰值。[FSDP生命周期推演](推演_FSDP参数生命周期.md)分别计算常驻72字节和反向120字节的简化账本。

它与TP、PP处理的约束不同：分片DP首先消除副本，TP分摊算子，PP分摊层与时间。真实方案经常组合它们，而不是在名字之间三选一。

## 2022—2023：状态装下后，激活与上下文再次成为瓶颈

扩大batch和上下文后，参数容量下降并不保证激活容量下降。Megatron相关工作提出序列并行与选择性重计算，针对TP之外重复保存的激活和高成本重算区域优化。[Reducing Activation Recomputation，2022](https://arxiv.org/abs/2205.05198)。

这里的SP主要改变部分算子的序列布局，不能直接理解为整个Attention都在独立的短序列上执行。长上下文需要访问远端K/V；Ring Attention用块化计算与环形交换组织长序列Attention。[Ring Attention，2023](https://arxiv.org/abs/2310.01889)。

新增问题包括在线softmax合并、因果mask、远端K/V梯度归还和负载不均。把序列平均切成两段，因果Attention的有效工作量不一定相等。[SP/CP推演](推演_SP与CP布局和梯度.md)给出10对26与18对18的对比；这些数字是指定mask下的有效位置计数，实际Kernel时间还受实现影响。

## 条件计算：专家容量与动态负载是另一条轴

MoE用不同token选择不同专家，使总参数容量和每token激活参数量分离。Switch Transformer展示了简化路由的大规模稀疏模型路线；专家并行要把token送到拥有对应专家的设备。[Switch Transformer，2021](https://arxiv.org/abs/2101.03961)。

路由结果使通信与计算量由输入动态决定。平均每卡token数量相同并不代表每个专家都均衡；增加专家也不能保证端到端更快。容量、token丢弃或无丢弃执行、路由权重、dispatch/combine顺序都是算法与系统的接口。[EP推演](推演_EP路由与多维通信组.md)展示同一个token分发到两个专家后如何恢复原序。

## 汇合：多维布局把局部优化变成边界问题

一个训练作业可以同时具有DP、TP、PP、CP和专家布局，但不能不加区分地把所有配置数相乘。各区域可能重用设备轴，某些参数复制，另一些参数分片。改变布局后最关键的问题是：下一算子期望哪个全局张量、哪个局部分片，以及谁拥有要更新的状态。

用下表定位瓶颈，比先选并行缩写更有用：

| 观察 | 优先分析的对象 | 引入方法后必须重新检查 |
|---|---|---|
| 模型状态放不下 | 参数、梯度、优化器副本 | gather峰值、通信量、owner |
| 单层计算或容量超限 | 算子内部张量维 | collective频率、本地矩阵形状 |
| 层很多且跨节点带宽有限 | stage分工 | 边界P2P、负载、激活、气泡 |
| 长序列激活超限 | token/head布局 | Attention依赖与mask |
| MoE尾部拖慢 | 专家token分布 | all-to-all与热点专家 |
| 算子快但step仍慢 | 依赖与通信关键路径 | 重叠是否真实、排队是否转移 |

这条历史的持续问题是**局部节省如何改变全局执行**。设备网格可以表达切分，不能替代对正确性、峰值容量和时间线的推导。
