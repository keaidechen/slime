# 采样、自回归依赖与推测解码

> 类型：基础机制。前置：[Transformer](../02_Model_Architecture/Transformer与Attention基础.md)。

## Logits 不是最终 token

模型输出词表 logits，经过规定的温度、屏蔽、截断或其他处理后形成采样分布。Greedy、top-k、top-p 是不同的决策或分布变换。返回的 logprob 需要说明对应原始模型还是处理后的分布。

停止 token、最大长度、约束解码和重复惩罚改变生成过程。RL 训练若需要行为策略概率，必须匹配实际采样语义，而不是仅保存任意一份模型 logits。

## 自回归的顺序依赖

下一个 token 的输入包含上一步结果，因此普通生成存在逐步依赖。增加 batch 能让不同请求并行，但不会自动消除单请求输出步骤之间的依赖。

推测解码让较便宜的过程提出多个候选，再由目标模型验证。候选可以来自独立 draft 模型或其他机制；具体方法对训练、状态和概率校正的要求不同。

## 精确采样校正的直觉

在一种标准构造中，候选由 q 采样，目标分布为 p，对候选 token x 以 $\min(1,p(x)/q(x))$ 接受；拒绝时依据归一化的正残差 $(p-q)_+$ 采样。完整多步算法还需要正确处理前缀条件和额外 token。

这说明接受规则属于正确性证明的一部分。简单接受“目标模型也觉得可能”的 token，不能自动保证目标分布不变。Greedy 一致性与随机采样分布一致性也应分别验证。

## 性能与状态成本

设一次 draft 加验证耗时为 $T_d+T_v$，平均提交 k 个 token，则粗略成本为 $(T_d+T_v)/k$。它必须与相同负载和质量条件下的基线比较。接受率高不保证加速：draft 太慢、验证形状不合适或 batch 已很大，都可能削弱收益。

拒绝候选后，KV 或递推状态需要回到接受前缀对应的状态。对于原地更新的有限状态模型，回滚方式尤其需要设计。还要核对随机数、位置和输出计数。

## 三token词表的精确接受与拒绝推演

用词表{a,b,c}，目标分布p=[0.5,0.3,0.2]，draft分布q=[0.2,0.5,0.3]。这里p/q都是相同已接受前缀下、规定采样处理之后的分布。

| 候选 | 被q提议的概率 | 条件接受概率min(1,p/q) | 无条件接受质量 |
|---|---:|---:|---:|
| a | 0.2 | 1 | 0.2 |
| b | 0.5 | 0.6 | 0.3 |
| c | 0.3 | 2/3 | 0.2 |

总接受概率0.7，总拒绝概率0.3。正残差(p−q)+=[0.3,0,0]，归一化后拒绝分支必选a。因此最终输出质量为a:0.2+0.3=0.5，b:0.3，c:0.2，恰好恢复p。

若拒绝时直接重新按p采样，最终质量则为[0.2,0.3,0.2]+0.3p=[0.35,0.39,0.26]，已经改变目标分布。这个反例说明“再问目标模型一次”不能替代正确残差校正。

## 多步候选的状态如何提交

设draft提出[x1,x2,x3]。目标模型可以在这些候选前缀上计算相应验证分布，但只有前面的候选被接受，后续分布才对应真实已提交前缀。

假设x1被接受、x2被拒绝并校正为y2，则提交输出[x1,y2]，x3作废。目标侧保留与原前缀+x1对应的有效KV；为x2/x3形成的候选后缀不能继续当作真实上下文。y2通常尚未经过下一次forward，其KV还未计算。若采用不同的fused执行，仍要满足同一逻辑长度与状态。

若所有候选都接受，经典方案还可从目标模型的最后一个分布采样额外token。这个额外token与普通decode刚采样出的token一样，不能因为已经输出就认为其KV已写入。分叉、拒绝与回滚因此要同时维护输出长度和已计算KV长度。

## 一组明确假设的成本比较

假设普通目标decode每步10 ms；每轮draft耗时4 ms，目标验证12 ms，其他成本忽略。若一轮平均提交2个token，摊销成本8 ms/token，相对该基线为1.25倍速度；若平均只提交1个，则16 ms/token，反而更慢。

这里的平均提交长度包含该算法允许的额外token；接受率、候选数与平均提交长度不是同一个统计量。服务负载、验证batch、draft位置变化后，所有时间都应重新测量。本例没有声称任何具体模型有此收益。

验证：[接受概率与成本脚本](../labs/training_rl_walkthroughs.py)；状态管理见[KV推演](推演_KV分页共享与取消.md)，调度背景见[推理运行时演进史](推理运行时演进史.md)。

## 演进边界

普通逐 token 生成简单但受依赖限制；多候选验证增加并行工作，代价是候选成本与状态管理；更紧密集成的预测结构减少某些开销，又引入模型训练或部署条件。应该同时记录接受长度、额外工作、端到端延迟和分布验证。
