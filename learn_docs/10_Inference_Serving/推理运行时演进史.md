# 推理运行时演进史：从执行一个batch到管理不断变化的状态

> 本文追踪通用自回归模型服务中的系统问题。日期标论文首次公开年份；下文因果串联是分析框架，不意味着各项技术按单一路线替代前作。性能数字必须回到原论文的负载与硬件，本页不搬用峰值倍数。

## 固定batch的假设为什么不适合生成

分类类任务通常经过一次模型调用就返回。自回归生成要反复执行，输出长度还不能事先精确知道。如果batch成员直到所有请求完成才变化，短请求退出后留下空位，新请求却仍排队。即使每次模型调用很快，请求层利用率也可能很差。

Orca在2022年提出iteration级调度，在迭代边界改变batch，并配合适合Transformer执行的选择性批处理。它把资源分配单位从完整请求细化到生成迭代。[Orca，OSDI 2022](https://www.usenix.org/conference/osdi22/presentation/yu)。

新问题是请求状态跨迭代存活：谁刚加入、谁刚结束、每条序列有多少KV、输出返回哪个请求。引擎必须能够重建变化后的批次元数据。连续批处理首先解决空位与等待，不能单独解决KV容量或长prefill干扰。

## 2023：动态批次使连续KV分配的浪费更明显

KV长度不断增长。若按最大输出长度预留连续空间，会浪费尚未使用的容量；若频繁调整连续空间，则要处理扩容和碎片。PagedAttention把逻辑KV块映射到物理块，并支持围绕块组织的共享与管理。[PagedAttention / vLLM，2023](https://arxiv.org/abs/2309.06180)。

新增成本是间接寻址、页表与分配器状态，以及共享后的引用和写入隔离。分页减少某类碎片，不等于KV变小，也不等于共享写入天然安全。页大小还影响尾部浪费和管理颗粒度。

[KV完整推演](推演_KV分页共享与取消.md)区分三个量：逻辑token数量、物理有效KV、已分配页容量。取消请求时还有设备在途引用，不能只把请求从列表中删除就回收页。

## 2023：相同前缀重复计算，缓存从请求私有变成跨请求资源

多轮对话、公共系统提示和程序化多次调用会重复访问同一前缀。SGLang的RadixAttention用前缀结构组织KV复用，并与结构化语言模型程序执行相结合。其预印本始于2023年，会议论文为NeurIPS 2024。[SGLang论文](https://arxiv.org/abs/2312.07104)。

这一步减少重复prefill，却引入缓存的保留与淘汰策略。高缓存命中率不一定意味着低尾延迟：活跃decode可能仍缺页，热门前缀也可能挤占其他请求容量。相同token前缀只有在权重、位置、adapter等语义相容时才可共享。

因此“请求都结束但显存未回落”可能是有意缓存；“缓存容量很大”也不能单独证明泄漏。需要同时看活跃占用、可淘汰缓存、预留池和设备正在访问的状态。

## 2024：prefill与decode混在一起，资源利用与延迟互相牵制

Prefill一次处理多个输入token，decode通常每条序列只推进一个token。两者的计算形状和延迟敏感点不同。把一个很长prefill直接插入decode批次，可能拉长正在生成请求的token间隔；完全让decode优先又可能使新请求长期等不到首token。

Sarathi-Serve利用分块prefill与混合批次调度控制迭代工作量，研究吞吐与延迟之间的折中。[Sarathi-Serve，2024](https://arxiv.org/abs/2403.02310)。新的限制是块大小、优先级与批次形状：token预算只是代理指标，等量token不保证等耗时；已经累积的KV长度也会改变decode成本。

[运行时批次推演](推演_调度批次与设备执行.md)展示预算6下如何同时推进三个请求。它刻意不把6 token转换成固定毫秒，因为那需要测量而不是算术替代。

另一条路线把两阶段部署到不同资源池。DistServe围绕prefill/decode分离组织并行策略与资源分配，目标是满足服务约束的有效吞吐。[DistServe，2024](https://arxiv.org/abs/2401.09670)。

分离后减少阶段干扰，却多出KV传输、目的端准入、两边队列和资源配比。网络不足、短请求占比高或负载低时，新增开销可能盖过收益。分块与分离也不是互斥：一个改变调度颗粒度，另一个改变放置位置。

## 执行层：动态请求为什么仍想使用静态图

调度器希望每步调整批次，设备执行又希望减少host提交开销。CUDA Graph预先组织设备操作与依赖，可降低反复发射的CPU开销；具体capture限制和更新能力须查对应版本。[CUDA Graph官方说明](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/cuda-graphs.html)。

这形成动态语义与可复用执行形状的接口：把实际请求映射到某个受支持bucket，填入合法元数据，执行后只返回真实请求输出。图中的dummy行不能变成真实样本，稳定地址也不意味着地址中的内容已准备好。

计算图编译、Kernel融合和CUDA Graph处理不同层面。融合减少算子边界，Graph减少重复提交，调度减少请求等待；三者可以组合，但一个层面的收益不能自动归给另一个层面。

## 另一条轴：减少串行生成轮数

Speculative decoding先产生候选，再由目标模型验证。经典随机采样方案通过接受概率与拒绝后的残差分布保持目标分布，而不只是“候选相同就接受”。[Leviathan等，2022](https://arxiv.org/abs/2211.17192)。

它引入draft成本、接受率波动、额外KV和验证批次形状。服务拥塞时更大的验证工作也可能改变其他请求延迟。减少主模型串行调用次数，不保证所有负载下单位GPU吞吐提高。详见[采样与推测解码](采样与推测解码.md)。

## 如何判断下一项优化是否有用

| 当前症状 | 可能对应的限制 | 单看什么容易误判 |
|---|---|---|
| 短请求等长请求 | 请求级固定批次或不合适的调度 | 仅看单次forward耗时 |
| 可用并发低 | KV预留、碎片、工作区 | 仅看模型权重大小 |
| 重复长前缀开销大 | 未复用前缀或缓存放置不当 | 仅看总体缓存命中率 |
| token间隔突然变长 | prefill干扰、队列或执行停顿 | 仅看平均tokens/s |
| 分离后首token更慢 | KV传输与双队列 | 仅看各资源池利用率 |
| GPU有细碎空洞 | host提交、同步或采样 | 仅看Kernel峰值性能 |

这些历史变化把运行时的职责从“执行张量”扩展到“维护请求身份、状态所有权与完成边界”。服务优化最后要回到到达分布、TTFT、token间隔、完成率和资源成本一起评价。
