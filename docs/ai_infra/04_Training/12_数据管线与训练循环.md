<a id="s1-一次训练-step目标梯度状态与更新"></a>

## 1. 一次训练 step：目标、梯度、状态与更新


前文已经解释梯度、状态容量与跨卡通信。这里将它们连成一次参数更新。这里的 **step** 默认指一次逻辑优化器更新，**microbatch** 是为装入显存而拆出的一小批数据；多次 microbatch 前后向可以累积成一次更新。

最短的执行链是：读数据 → 前向预测 → 算 loss → 反向求梯度 → 汇合全部梯度贡献 → 更新参数 → 清理本轮梯度。训练框架可以交叠独立工作，但后一轮使用的参数必须符合选定的更新规则。

<a id="s1-先定义训练目标"></a>

### 先定义训练目标

给定样本和 mask，loss 必须说明是按序列、样本还是有效 token 平均。mask 在这里标识哪些 token 计入损失，不要与限制 Attention 可见位置的 mask 混为一谈。对有效 token 集合 V，可写 $L=\sum_{t\in V}\ell_t/|V|$。例如一批有 8 个位置、其中 2 个是补齐位置，则分母应为 6。不同数据并行 rank 的有效 token 数可能不同，因此归一化与梯度规约需要一起设计。

一个 step 通常包含获取数据、前向、loss、反向、梯度处理、参数更新以及必要的同步。实现可能流水化这些阶段，但不能破坏数据依赖和更新语义。

<a id="s1-优化器为什么需要额外状态"></a>

### 优化器为什么需要额外状态

第 5 章已经推导了 SGD、动量与 AdamW。这里使用其中的状态结论：Adam 保存一阶矩与二阶矩，学习率调度和更新计数也影响后续行为；这些状态必须随参数一起保持相容。清空历史虽然减少持久状态，却改变了学习过程。

本章继续关注更新顺序与系统边界，完整公式见[损失、自动微分与优化器](../02_Model_Computation/05_损失自动微分与优化器.md#s2)。

<a id="s1-常驻状态与峰值状态"></a>

### 常驻状态与峰值状态

可以沿一次更新追踪显存：开始时参数和优化器历史已经存在；做前向时逐层产生激活，反向需要读取其中一些；做反向时又写入或累加梯度。当某层反向不再需要其激活，相关存储才可释放。若还有下一份 microbatch，梯度必须保留并继续累加，直到这次逻辑更新结束。

通信和算子还可能临时申请缓冲，并与上述对象同时存活。峰值通常出现在这些生命周期重叠的时刻。因此下载的参数文件大小只能解释一部分显存占用，不能直接当作训练所需容量。

假设 1B 参数采用 BF16 参数、FP32 梯度、FP32 主权重和两个 FP32 Adam 矩，状态合计约 18 GB，尚未计激活和临时 buffer。这是明确精度假设的账本，其他实现可以不同。

<a id="s1-一次正确更新的检查点"></a>

### 一次正确更新的检查点

梯度裁剪把过大的梯度按比例缩小；非有限值指 NaN（不是有效数值）或 Inf（无穷大）。Loss scaling 是先放大损失和梯度、更新前再缩回原单位的低精度训练技术。Owner 指负责更新某片参数及其状态的参与者；Checkpoint 指用于重启恢复的持久化快照，不是激活重计算。

1. 数据与 mask 对应预期目标，packing 不越过样本边界。
2. 梯度累积与跨 rank 规约得到目标需要的缩放。
3. 梯度裁剪、非有限值处理与 loss scaling 遵守算法顺序。
4. owner 使用相容的参数、梯度和优化器状态更新。
5. 后续消费者读取正确版本，Checkpoint 捕获相容状态。

<a id="s1-扩展带来的新问题"></a>

### 扩展带来的新问题

模型扩大使状态容量突出，分片降低副本开销，却引入 gather 和 owner 更新；长序列扩大激活，重计算减少保存却增加计算；流水线提高设备利用，却增加在途 microbatch 和调度状态。

“更快 step”与“更快达到目标质量”是不同指标。改变 batch、优化器或样本分布之后，需要重新评估收敛，而不能只比较相同步数耗时。

实现入口：[Megatron 训练主线](<../appendices/source/megatron/01_foundations/02_training_mainline.md>)、[优化器与状态](<../appendices/source/megatron/03_state_and_memory/01_data_parallel_optimizer_checkpoint.md>)。

参考：[Adam](https://arxiv.org/abs/1412.6980)、[ZeRO](https://arxiv.org/abs/1910.02054)。


<a id="s1-一次完整更新从缩放梯度到adamw与跳步"></a>

### 一次完整更新：从缩放梯度到AdamW与跳步

> 本节可在本节直接手算；跨 rank 的梯度来源将在后续[DDP 梯度推演](<14_数据并行与状态分片.md#s2-数值展开-ddp不等长数据梯度累积与-bucket-时间线>)展开。本例用两个标量主权重，模拟两个owner的分片状态；数值运算按实数计算，不模拟BF16舍入或真实collective。

<a id="s1-把一个step拆成三个计数"></a>

#### 把“一个step”拆成三个计数

Microbatch编号表示这次更新累积了几次前后向；优化器step表示成功更新了几次状态；数据游标表示已经提交消费了哪些样本。遇到非有限梯度时，这三者可能不一起增长，学习率和checkpoint必须声明使用哪种计数。

本例在完整累积后处理梯度，每个参数的全局目标梯度已通过正确归约得到。两个owner分别拥有w0=1和w1=2，初始一阶、二阶矩均为0。逻辑全局梯度为[3,4]，本轮loss scale=8，暂存在buffer中的梯度因此为[24,32]。

<a id="s1-先完成归约与unscale再定义全局norm"></a>

#### 先完成归约与unscale，再定义全局norm

| 阶段后 | owner 0梯度 | owner 1梯度 | 说明 |
|---|---:|---:|---|
| 已累积、已按目标归约，仍带scale | 24 | 32 | 示例从这一步开始，不再次除DP度 |
| unscale，除以8 | 3 | 4 | 梯度恢复到优化目标的单位 |
| 各owner计算平方和 | 9 | 16 | 每个逻辑参数恰好计一次 |
| 合并平方和 | 25 | 25 | 共享全局裁剪决策 |
| 全局norm | 5 | 5 | sqrt(25) |
| 按阈值2.5裁剪 | 1.5 | 2 | 统一乘min(1,2.5/5)=0.5 |

若每个owner各自裁剪到2.5，得到[2.5,2.5]，全局norm约3.536，既没达到阈值，也改变了方向。如果把完整DP副本的平方和重复相加，同一参数又会被算多次。TP中复制的参数、FSDP分片和PP跨stage参数都要服从“逻辑上每个参数计一次”。

AMP（Automatic Mixed Precision，自动混合精度）的标准流程要求先unscale再做未缩放单位下的梯度裁剪；累积期间不要在部分microbatch之间随意切换scale。[PyTorch AMP示例](https://docs.pytorch.org/docs/stable/notes/amp_examples.html)。真实分片实现可融合操作或调整通信顺序，只要保留同一语义。

<a id="s1-adamw逐项计算"></a>

#### AdamW逐项计算

设学习率η=0.1，β1=0.9，β2=0.99，weight decay λ=0.1。为了可手算，epsilon取0；本例二阶矩均非零，生产实现通常使用正epsilon。两个权重都在decay组，优化器step从t=1开始。

使用裁剪后的g=[1.5,2]：

- m1=0.9×0+0.1g=[0.15,0.2]。
- v1=0.99×0+0.01g²=[0.0225,0.04]。
- 偏差校正m̂1=m1/(1−0.9)=[1.5,2]。
- 偏差校正v̂1=v1/(1−0.99)=[2.25,4]。
- 自适应方向m̂1/sqrt(v̂1)=[1,1]。

解耦衰减形式为w新=(1−ηλ)w旧−ηm̂/(sqrt(v̂)+epsilon)，因此：

| 参数 | 衰减后的旧权重 | 自适应减量 | 新主权重 |
|---|---:|---:|---:|
| w0 | 0.99 | 0.1 | 0.89 |
| w1 | 1.98 | 0.1 | 1.88 |

AdamW的衰减没有加入本例的m/v计算。把λw加进梯度后再做Adam，是另一种更新规则。[Decoupled Weight Decay Regularization](https://arxiv.org/abs/1711.05101)。

随后将主权重转换成计算权重，或在下一次使用前物化对应分片。下一轮m/v必须继承[0.15,0.2]和[0.0225,0.04]，不能只加载w就宣称完整恢复训练。

<a id="s1-下一轮某个owner出现inf"></a>

#### 下一轮某个owner出现Inf

假设下一轮owner 0梯度有限、owner 1出现Inf。本例选择全作业跳过更新的协议：所有参与者共同得到skip=true，各自清空本轮无效梯度、按统一规则调整scale；w、m、v和成功更新计数维持上一轮结果。

如果owner 0单独更新，owner 1跳步，同一个模型的参数就来自两次不同的优化器决策。NaN/Inf检测的作用域必须覆盖这次逻辑更新涉及的所有状态owner，不能只检查当前rank。

本例学习率调度随成功更新推进，skip时不推进；数据已经读取但是否重放，另由数据协议规定。其他系统可以选择不同的计数方式，文档和恢复状态必须与其一致。

<a id="s1-内存与调度如何接入这条过程"></a>

#### 内存与调度如何接入这条过程

梯度累积结束前不能清空需要保留的贡献；裁剪结束前不能提前执行一部分Adam更新；异步checkpoint也不能一边读取m/v一边让下一步原地改写它们。计算、通信或落盘可以重叠，但重叠必须围绕这些读写依赖安排。

该算例的目标是检查更新语义，不是证明哪种融合优化器更快。性能分析另记录：梯度ready、归约完成、norm完成、optimizer完成、下一次前向开始等事件。

验证：[训练与RL数值脚本](<../examples/training_rl_walkthroughs.py>)。恢复语义见第 18 章：[数据游标与恢复](<18_Checkpoint与故障恢复.md#s2-数据游标与checkpoint提交>)。

## 2. 训练数据管线：从样本到持续供给的 microbatch


<a id="s2-数据也有关键路径"></a>

### 数据也有关键路径

数据经历读取、解码、tokenization、采样、batch 构造、主存准备和设备传输。GPU 等待可能来自任何阶段，也可能来自队列与线程竞争。提高 GPU 算力不会自动提高数据供应速度。

预处理可以提前执行并复用，但需要记录 tokenizer、模板和数据版本。在线生成的数据则具有不同的到达率和长度分布，见[RL 队列](<../06_Post_Training/27_权重发布异步与资源调度.md#s4>)。

<a id="s2-paddingpacking-与长度分桶"></a>

### Padding、Packing 与长度分桶

Padding 将不等长样本扩到共同长度，方便规则计算但产生无效工作。Packing 把多个样本放进同一 token 容器，必须保存 attention 边界、位置、loss mask 和样本归属。

假设长度为 100、100、800 的三个样本全部 padding 到 800，会处理 2400 个位置，其中有效 token 为 1000。Packing 可以减少某些浪费，但不能默认跨样本 attention 合法，也不能只根据 token 数推断 Attention FLOP。

长度分桶降低 padding，却可能改变数据混合与随机性。动态 batch 需要维护全局有效 token 数、梯度归一化和运行时形状变化。

<a id="s2-多源采样与分布式分片"></a>

### 多源采样与分布式分片

混合比例必须说明按样本、输入 token 还是有效预测 token 统计。设来源 A 的样本长度为 100，B 为 900，各取一半样本，在所有位置都有效且忽略边界差异的教学假设下，B 占约 90% token。若目标是一半 token 来自 B，长期样本数应约为 A:B=9:1。SFT 的 prompt mask 会进一步改变有效预测比例。

RNG（Random Number Generator，随机数生成器）具有随抽样推进的内部状态。仅保存初始 seed 不能恢复已推进的位置，重计算和恢复训练通常还需保留状态及对应的消费顺序。

采样器决定选哪些逻辑样本，DP/worker 分片决定谁读取它们，packing 决定怎样放入张量。这三个层次应分别记录：数据 revision、来源、样本 ID、采样 RNG、分片规则和 pack offsets。TP/PP 同一模型执行组所需的数据一致性由框架协调，不能把所有 rank 当成独立 DP 数据消费者。

对 iterable 数据源，多 worker 若各自从头读取同一流，会产生重复；需要显式分片。worker 数、DP 度或长度分桶改变后，恢复必须重建同一全局采样规则，或者声明允许顺序改变。PyTorch 的 [IterableDataset](https://docs.pytorch.org/docs/stable/data.html#torch.utils.data.IterableDataset)说明了多 worker 副本的分片责任。

<a id="s2-packing的目标边界与有效分母"></a>

### Packing的目标、边界与有效分母

> 两个独立样本的教学算例，按实数核算 loss；不执行 varlen kernel。若语料目标允许跨文档上下文，应另行定义边界。

<a id="s2-先明确打包前到底优化哪些预测"></a>

#### 先明确打包前到底优化哪些预测

样本A为[BOS,a,b,EOS]，样本B为[BOS,c,EOS]。先考虑各样本内部的next-token预训练目标：A有3个预测，B有2个预测，不跨样本预测下一个BOS。

将它们拼成7个输入位置，logits位置i用于预测i后面的目标：

| logits位置 | 输入token | 标签 | 预训练loss mask | 样本内position |
|---|---|---|---:|---:|
| 0 | A:BOS | a | 1 | 0 |
| 1 | a | b | 1 | 1 |
| 2 | b | EOS | 1 | 2 |
| 3 | A:EOS | ignore | 0 | 3 |
| 4 | B:BOS | c | 1 | 0 |
| 5 | c | EOS | 1 | 1 |
| 6 | B:EOS | ignore | 0 | 2 |

“没有目标的位置”不是词表里的一个真实ignore token；实现可以用忽略标签或显式mask，但必须保证无效标签不被非法gather访问。

<a id="s2-attention边界与loss边界是两件事"></a>

#### Attention边界与loss边界是两件事

正确的独立样本causal可见集合为：位置0可见{0}，1可见{0,1}，2可见{0,1,2}，3可见{0,1,2,3}；位置4只能见{4}，5见{4,5}，6见{4,5,6}。

只重置position ids不足以隔离A与B；只屏蔽A末尾loss也不足以阻止B关注A。实现需要block causal mask或能够表达等价序列边界的varlen元数据。反过来，若训练目标本来就是把文档连接为连续语料流，允许跨边界就是不同且可能有意的目标，本页不混用两者。

Packing改变物理布局；要保持目标不变，还需保持样本身份、标签、mask、位置规则和有效token计数。不能把总输入长度7当成有效预测数5。

<a id="s2-把分母算清楚"></a>

#### 把分母算清楚

假设A的三个有效loss为[0.1,0.2,0.4]，B的两个为[0.6,0.8]。按有效token平均的全局loss为(0.7+1.4)/5=0.42。

若两个DP rank分别处理A、B，各自mean后再平均，结果是(0.7/3+1.4/2)/2≈0.466667。这是按样本均值平均，改变了权重。正确的反向缩放见[DDP推演](<14_数据并行与状态分片.md#s2-数值展开-ddp不等长数据梯度累积与-bucket-时间线>)。

再改成SFT目标：A的prompt是[BOS,a]，只训练[b,EOS]；B的prompt是[BOS]，训练[c,EOS]。此时位置0的mask改成0，其余有效位置为1、2、4、5，分母变成4，相应loss=(0.2+0.4+0.6+0.8)/4=0.5。

真实场景还可能屏蔽工具返回或被截断片段。应先决定哪些输出是要优化的动作，再让packing搬运这些定义。

验证：[Packing 数值参考](<../examples/training_rl_walkthroughs.py>)。下面的供给管线可以预取这些样本，但读入不等于训练消费；提交时序见[数据游标与 Checkpoint](<18_Checkpoint与故障恢复.md#s2-数据游标与checkpoint提交>)。

### Mask 为零为什么仍可能污染梯度

一个被排除的位置若已经产生 NaN，最后乘零并不能把它安全抹去：浮点运算中 $0\times\mathrm{NaN}$ 仍是 NaN。类似地，无效 token ID 先参与 gather，之后再乘 loss mask，也不能补救越界访问。

所以“无效位置不参与目标”要落实到整个计算路径。构造标签时先给被忽略位置一个合法索引，或使用明确支持 ignore index 的损失接口；计算比率、除法和归一化时，先避免在无效位置产生非法值，再按 mask 汇总。不能为了让程序继续执行，把所有非有限值替换为零，这会掩盖真实有效位置的故障。

特别考虑全空批次：若有效数量 $N=0$，$\sum\ell/N$ 没有定义。数据管线应把它交给显式的空批协议，而不是临时把分母改成 1 就继续优化。后面的数据并行还要求所有 rank 就此作出相容决定；本地没有有效位置不代表全局没有有效数据。

对 packing 的最小验收可以这样做：固定两条样本，比较独立执行与打包执行的有效 logits、逐参数梯度和一次更新；再只修改第一条样本，确认第二条的结果在声明的独立边界下不变。这既验证数值，也直接验证了跨样本信息是否泄漏。

<a id="s2-预取与背压"></a>

### 预取与背压

预取队列允许数据 worker 提前准备 batch，训练端需要时直接取用。例如训练每 100 ms 消费一批，而一次读取偶尔停顿 200 ms，事先准备好的两批可以覆盖这段短暂停顿。若数据端长期每 120 ms 才能产出一批，队列迟早仍会耗尽：预取能够平滑波动，不能弥补持续的供给不足。

队列满时让生产方等待，称为背压；它防止数据准备无限领先于训练而耗尽主存。队列上限也应反映对象大小：两批短文本和两批视频占用可能相差很大，因此限制 batch 数之外，还应限制在途字节或 token，并把正在传输和正在消费的缓冲算进去。

pinned memory（页锁定主机内存）在注册期间保持物理页稳定，可供某些异步 DMA 路径使用。它消耗主机资源，是否真正与计算重叠还取决于设备、stream 依赖和缓冲区生命周期。

Pinned host memory 常用于特定异步设备传输路径，但会消耗系统资源；非阻塞提交是否真正重叠，取决于来源内存、设备能力、stream 依赖和其他工作。

<a id="s2-供给速率与设备等待"></a>

### 供给速率与设备等待

H2D（Host-to-Device）是从主机内存向设备内存传输，D2H 是反向传输。提交复制的 CPU 调用返回，与设备已完成复制，是两个不同事件。

设每个更新消费 8192 个有效 token，无数据等待时计算耗时 0.2 秒，消费能力为 40960 token/s。若数据管线持续只供给 30000 有效 token/s，则长期更新间隔至少为 8192/30000≈0.273 秒；有限预取队列只能延后饥饿，不能改变这个稳态上界。这里忽略 packing 和搬运开销，实际应分别测量读取、构造、H2D 与训练关键路径。

按输入字节、媒体大小和有效 token 同时限制预取。一个 batch 的数量相同，长序列或视频样本仍可能占更多主存。Pinned memory 和异步 H2D 的收益需核对 stream 依赖；CPU 解码、tokenization 和 pack 构造也可能互相争用线程。

<a id="s2-演进中的取舍"></a>

### 演进中的取舍

| 问题 | 方法 | 新问题 |
|---|---|---|
| 每 step 同步读取拖慢训练 | worker 与预取 | 随机状态、重复读取、内存 |
| 变长样本浪费计算 | packing 与分桶 | 边界、mask、负载差异 |
| 单机读取无法扩展 | 分布式数据分片 | 全局去重与样本顺序 |
| 训练中断需要继续 | 保存采样器与进度 | 数据版本与恢复一致性 |

<a id="s2-可观测与恢复"></a>

### 可观测与恢复

记录读取和构造时延、队列深度、有效 token、padding 比例以及设备等待。恢复时仅保存 global step 可能不足以定位数据进度；异步预取已经消费但尚未训练的样本也需要约定处理方式。

参考：[PyTorch DataLoader](https://docs.pytorch.org/docs/stable/data.html)、[CUDA notes](https://docs.pytorch.org/docs/stable/notes/cuda.html)。

<a id="s3-数据读取与存储吞吐从文件到设备输入"></a>

## 3. 数据读取与存储吞吐：从文件到设备输入

训练的数据语义见[数据管线](<#s2>)。本节追踪同一份数据在存储、主存和设备之间的路径，并把吞吐、缓存与版本放进同一份账本。

<a id="s3-文件大小为什么会改变供给能力"></a>

### 文件大小为什么会改变供给能力

设一次读请求有固定延迟 ℓ，连续带宽为 B，返回 s 字节，则不重叠时吞吐上界为 s/(ℓ+s/B)。教学假设 ℓ=5 ms、B=1 GB/s，读 1 MB 耗时 6 ms，约 167 MB/s；读 100 MB 耗时 105 ms，约 952 MB/s。单位均为十进制，尚未计算解析、限流和共享资源。

合并小文件可以摊薄请求与元数据成本，但过大的 shard 会降低随机访问粒度、增加重试和尾部负载。若多个 worker 竞争同一出口，增加并发不可能无限放大带宽。样本逻辑 ID 应独立于物理文件位置，才能在重分片后保持可追踪。

| 存储层 | 可获得的收益 | 需要计入的成本 |
|---|---|---|
| 本地 NVMe | 本地读取与缓存，减少共享出口压力 | 预热、容量、节点丢失后的重建 |
| 共享文件系统 | 多节点共享命名空间 | 元数据负载、并发读写、热点与尾延迟 |
| 对象存储 | 对象化分片和远端容量 | 请求延迟、range 请求、下载缓存和重试 |
| 主存缓存 | 避免重复读取或解析 | 内存、进程副本、失效与版本身份 |

这些是设计轴，不是产品速度排序。必须用实际文件大小、并发和读写混合测量。

<a id="s3-mmappage-cache-与冷暖状态"></a>

### mmap、page cache 与冷暖状态

`mmap` 将文件映射进虚拟地址空间；创建映射不意味着所有页已读入物理内存。后续访问可能触发缺页和 I/O。映射能减少某些显式复制，但不会消除存储读取、格式解压或 tokenization。接口示例见 [Python mmap](https://docs.python.org/3/library/mmap.html)。

Page cache 可让第二轮文件读取主要由内存满足。应用对象缓存还能省掉 JSON 解析／反序列化，与操作系统页缓存不是同一层。一次程序退出也不必然清空页缓存。基准报告应区分应用缓存冷／暖、OS 缓存状态已知／未知、远端缓存状态已知／未知；不能因为首次运行就标成冷盘测试。

预读适合可预测访问。全局 shuffle、压缩块或碎片化随机读可能改变有效性。可采用“打乱 shard 顺序＋有界样本缓冲”等折中，但它改变随机化方式，需在数据目标和恢复协议中记录。

<a id="s3-分阶段供给与重叠"></a>

### 分阶段供给与重叠

一批数据依次经过读取、解码、tokenize／pack、主存准备、H2D 和计算。严格串行时各段时间相加；在足够缓冲、独立资源且能正确重叠的理想流水线中，稳态间隔受最慢阶段限制，首批与尾批仍有填充／排空成本。

教学例每批读取 12 ms、解析 20 ms、H2D 4 ms、计算 10 ms。串行共 46 ms；理想四阶段流水的稳态间隔仍至少 20 ms。把计算缩到 5 ms 不改变这个供给上界。两个解析 worker 只有在 CPU、内存带宽、解释器或进程通信不成为新约束时才可能把解析阶段吞吐提高一倍。

Pinned memory 为某些异步 DMA 路径提供前提，`non_blocking` 只表达提交行为；是否隐藏 H2D 还取决于 stream 依赖和缓冲区生命周期。NUMA 放置影响 CPU 内存到 GPU/NIC 的路径，worker 数和线程数应与 CPU 配额一起记录。PyTorch worker、预取和 iterable 数据分片的接口边界见 [DataLoader](https://docs.pytorch.org/docs/2.14/data.html)。

若每个预取 batch 占 64 MiB，8 个 worker 各预取 2 批，排队负载就可能达到 1 GiB；还没有包含正在消费的 batch、进程副本和 pinned 副本。对变长媒体，按字节限制通常比只按 batch 数更有解释力。

<a id="s3-checkpoint-与训练读取竞争"></a>

### Checkpoint 与训练读取竞争

假设共享存储出口持续可用 2 GB/s，训练读取需要 1.2 GB/s，另有 80 GB checkpoint 要写入。同一出口的简化流量模型中，要完全不侵占训练份额，保存速率最多为 0.8 GB/s，至少需要 100 秒。若要求 40 秒内写完，就已消耗 2 GB/s，无法同时满足原读取需求。

真实读写是否共享同一瓶颈须由设备、网络和缓存证据确认；“异步保存”只把提交与完成解耦，不会产生额外带宽。可以限制上传速度、先写本地盘或分批提交，但要重新定义节点丢失时能恢复到哪里。持久化要求见[恢复语义](<18_Checkpoint与故障恢复.md#s1>)。

<a id="s3-数据身份与恢复需要哪些字段"></a>

### 数据身份与恢复需要哪些字段

保存 dataset revision、shard 内容 hash、样本 ID、tokenizer／processor revision、模板、过滤规则、采样随机状态和 pack offsets。数据清洗与去重策略改变样本集合，近似去重还应记录阈值和误判检查。训练、校准与独立评估集合需要检查重叠，不能只按文件名判断。

缓存键必须包含会改变输出的预处理版本；相同文件名或 URL 不能代替内容身份。恢复游标指向已提交的训练消费边界，预取到主存的数据不自动算作已训练。若允许恢复后改变采样顺序，应明确放弃哪一级重现保证。

<a id="s3-一个可以真正执行的诊断过程"></a>

### 一个可以真正执行的诊断过程

先固定样本顺序，记录每批各阶段时间与输出 hash。分别做：原文件读取、预读原始字节、缓存解析对象、固定已构造 batch 四种对照。每一步只消除相应阶段；若跳过 tokenization，也要验证得到的 token／mask 相同。

[CPU 实验](<../07_Practice/30_训练综合案例.md#s3>)实际比较“逐轮解析合成 JSONL”和“复用已解析对象”，保存原始重复测量和时间线。这只能定位该小型 CPU 程序的读取／解析成本。要解释 GPU 空闲，还必须关联真实 H2D、kernel 和队列；不能把 CPU 加速比直接移到训练端到端。


## 本章回顾
