# Omni 扩展阅读路线：从媒体表示走到实时系统

Omni 通常指跨多种模态理解或生成的模型与系统，中文常称“全模态”。这里沿用 Omni 拼写。这个名称没有统一的能力清单：支持音视频输入，不代表可以生成视频；能逐块返回音频，也不代表能一边说话一边理解用户的打断。

本支线目前是扩展阅读，保留原有 [26 篇默认主线](系统阅读路线.md)。它复用主线的张量、反向传播、KV、调度和性能分析知识，再补齐媒体表示、时间对齐、生成状态与交互语义。未来进入主线时，可以直接引用这些概念正文，不需要把模型产品介绍改写成基础教材。

## 两个贯穿案例

**案例 A：听完 10 秒音频，再流式回答。** 第二篇计算输入表示和字节，第三篇连接编码器、语言骨干、语音生成器与波形解码器，第四篇展开首音频、播放缺口和打断，第五篇分配阶段资源。该基线先讲轮流说话；全双工是额外能力，第四篇再解释它增加了哪些状态。

**案例 B：由文本与可选参考图生成一张图。** 第三篇从条件编码、初始噪声、迭代更新讲到图像解码，第五篇说明任务如何共存，第八篇推演并行、缓存和取消。选择图像是为了先看清完整生命周期；视频在此基础上增加时间维、跨帧依赖和输出同步。

共同约定：MiB = 2²⁰ 字节，KiB = 2¹⁰ 字节；教学 BF16 按每元素 2 字节核算；除特别说明，shape 省略 batch=1。语音算例采用**假设的** 50 帧/秒、8 个码本，绝非 Qwen3-Omni 或其他模型的默认配置。所有延迟是离散教学输入，不是设备实测。

## 不运行模型也能核对什么

[omni_walkthroughs.py](../examples/omni_walkthroughs.py)只使用 Python 标准库，核对表示尺寸、残差量化、播放时间线、乱序/重复/过期块、在途资源释放、损失梯度、阶段容量与迭代恢复。每个结果在正文中都有假设和解释，脚本不能证明语音自然度、GPU 性能或真实框架的容错能力。

读完可用四个问题自测：4000 个 codec 索引一定需要 4000 次串行解码吗？RTF 小于 1 为什么仍会卡顿？取消返回后显存一定可以释放吗？20 步媒体生成能直接当作生成 20 个文本 token 吗？答案分别见第二、第四、第五和第三篇。
