# Agent 训练与 Harness：从任务执行走到策略更新

这条支线以单个 coding agent 为贯穿对象，解释模型怎样在工具环境中完成任务，以及这段执行怎样成为可训练、可比较的证据。Harness 指组织模型调用、上下文和工具交互的运行层；其职责与模型服务、环境和训练器的区别由第一篇展开。

先读 [RL 系统全景](../11_RL_Systems/RL系统全景.md)和[算法与系统接口](../11_RL_Systems/RL算法与系统接口.md)，能区分生成、奖励、损失和参数更新后即可进入。本支线复用既有轨迹、概率、环境与评估正文；默认 [26 篇主线](系统阅读路线.md)仍负责共同基础。

## 用同一个任务检查三种变化

设教学任务是修复一个仓库中的失败测试。Agent 读取代码、修改文件、运行测试，再交付结果。沿这次执行分别考虑：

- **上下文变化。** 工具日志过长时，harness 裁剪日志或压缩历史。下一轮真正输入给模型的 token 应如何记录？完整事件日志为什么不能直接替代它？先读第 1、2 篇。
- **训练表示变化。** 一次任务导出多个训练片段后，共享前缀是否重复计入梯度？长轨迹是否仅因 token 更多而获得更大权重？先读第 3 篇，再核对第 7 篇的实现。
- **执行与评估变化。** 工具超时后重试、预算耗尽或环境创建失败，哪些属于任务失败，哪些属于未能取得结果？模型改善和 harness 改善如何分别比较？先读第 5、6 篇，再回到第 3 篇的对照设计。

这些是固定假设下的阅读问题，不宣称当前实现具备自动摘要、动作幂等或完整故障恢复。具体已有行为与需要额外设计的协议在案例中分开说明。

## 从执行记录到证据

每次比较需要同时固定任务切分、模型身份、harness 配置、工具环境、判分规则和预算。改变其中一项时，明确它是实验变量；采集任务级结果、实际模型输入输出、失败原因和资源消耗。吞吐增加只说明执行更快，独立评估才能检查训练是否改善任务表现。

通用正文中的小算例用于检查输入、权重与分母；案例的[独立源码清单](../reference/agent_source_manifest.json)用于定位本次核对的实现。它们不替代真实沙盒运行、GPU 训练或模型质量测量。统计方法继续读[实验统计与质量评估](../12_Performance_Reliability/实验统计与质量评估.md)。
