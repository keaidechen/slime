## 1. Transformer 执行与 KV 基础


训练用梯度改参数；推理固定参数，根据输入预测输出。Serving（模型服务）还需要接收请求、排队、返回结果和回收资源。本节先跟踪一条请求，第 20 章再管理多条请求的共享显存。

Prompt 是用户输入及系统模板形成的 token 序列；Prefill（预填充）计算输入序列，Decode（逐步解码）消费新 token 并继续预测。Dense Transformer 指这里每个 token 使用相同的稠密层，区别于选择部分专家的 MoE。

Token 是分词器（tokenizer）词表中的一个编号，不必对应一个汉字或一个单词。本章用 `[A,B,C]` 代表三个 token ID，字母只是便于跟踪的位置标签。模型一次前向（forward）接收编号、位置和历史状态，返回下一 token 的分数；生成循环再决定选谁、是否继续。下面默认仅文本、因果自注意力、固定模型参数且关闭训练时的随机 dropout；滑窗、交叉注意力和其他状态模型需另算。

本章的小张量、概率和耗时均为可复算的教学设定，不是实际模型输出或硬件基准。公式先在精确算术下说明语义，部署时再考虑浮点误差与后端实现。

<a id="s1-先画一个-dense-transformer-block"></a>

### 先画一个 Dense Transformer block

令 batch 为 B、序列为 S、hidden 为 H，输入为 [B,S,H]。Q/K/V 投影得到每个 token 的头向量；attention 混合可见 token，再由输出投影回到 H；MLP 先扩张再回投影，残差连接要求输出与输入形状相容。LayerNorm/RMSNorm、激活和位置编码也消耗算子与内存，不能只数大矩阵乘。

PyTorch Linear 的权重通常存为 [out_features,in_features]，数学写 XW 时 W 常定义为 [in,out]。读 TP 代码前先约定方向，否则“按行/列切”容易说反。

训练会为 backward 保存或重算 activation；推理通常不建训练图，但 decode 会跨步保留 KV。GQA 的 query head 数和 KV head 数不同，KV 核算要用后者。packing 后的总 token 数相同，也不表示 attention 可见 pair 数相同。

先把这些符号变成可以画在纸上的形状。$B$ 是同批序列数，$S$ 是每条序列本轮输入的位置数，$H$ 是隐藏向量的特征数；它们都是计数，不是字节。设 $B=1,S=3,H=4$，用两个查询头、两个 KV 头，每头维数 $d_h=2$。这是多头注意力 MHA（Multi-Head Attention）的一个小例子。

| 步骤 | 输入与权重 | 输出形状 | 这一维表示什么 |
|---|---|---|---|
| 编号查 embedding 表 | 编号张量形状 `[1,3]`，表 `[V_vocab,4]` | `[1,3,4]` | 每个位置变成四维向量 |
| Q/K/V 投影 | 三个权重各为 `[4,4]` | 各 `[1,3,4]` | Q 用于发起查询，K 用于匹配，V 提供被混合的内容 |
| 拆头并换轴 | `[1,3,4]` | 各 `[1,2,3,2]` | 依次为 batch、head、位置、头内特征 |
| 每头注意力 | Q、K、V | `[1,2,3,2]` | 每个查询得到一个加权后的向量 |
| 合头及输出投影 | 合头 `[1,3,4]`，权重 `[4,4]` | `[1,3,4]` | 恢复残差路径所需形状 |
| 简化两层 MLP | `[4,8]`，逐元素激活，再 `[8,4]` | `[1,3,8]` → `[1,3,4]` | MLP 是逐位置的多层感知机 |

真实模型可能使用带门控的 MLP，因此此表只说明基本维度关系。归一化调整每个位置向量的数值尺度；残差将子层输入与输出相加，故最后一维必须一致。最后一层之后，词表投影 `[H,V_vocab]` 将隐藏向量变成 logits，逻辑形状为 `[B,S,V_vocab]`；只生成首 token 时通常只需最后一个有效输入位置的那一行。词表大小 $V_{vocab}$ 与注意力的 Value 矩阵 $V$ 是不同对象。

GQA（Grouped-Query Attention，分组查询注意力）让多个 Q 头共用一组 K/V；MQA（Multi-Query Attention，多查询注意力）只保留一组 K/V。例如仍有 2 个 Q 头，但仅 1 个 KV 头，$W_Q$ 为 `[4,4]`，$W_K,W_V$ 各为 `[4,2]`，K/V 为 `[1,1,3,2]`。注意力仍输出两个查询头，KV 元素却减半。不能把两个 Q 头误算成两份必须存储的 KV，也不能直接把一个已训练 MHA 模型的头删掉就宣称计算等价。

上面采用数学上的 $XW$ 方向；[PyTorch Linear 文档](https://docs.pytorch.org/docs/stable/generated/torch.nn.Linear.html)采用 $xA^T+b$，存储的 $A$ 为 `[out,in]`。两种写法描述同一个线性映射，不是两种并行算法。


<a id="s1-为什么-llm-推理必须理解-prefill-与-decode"></a>

### 为什么 LLM 推理必须理解 Prefill 与 Decode？


一个请求：

```text
Prompt: 1000 tokens
```

推理通常分为两阶段。

<a id="s1-prefill"></a>

##### Prefill

计算整个 prompt；工程上也可分块执行。最后一个输入位置的 logits 可以直接用于采样首个输出 token，所以首 token 通常来自 prefill 的末尾，而不是必须额外做一次 decode。

此时：

```text
Q length ≈ 1000
K/V length ≈ 1000
```

有大量大矩阵乘法，GPU 并行度较高。

<a id="s1-decode"></a>

##### Decode

随后把刚采样的 token 作为下一次输入，补上它的 KV，再预测下一个 token。以下是不使用推测解码的单请求例子：

```text
Q length = 1
K/V length = 1001
```

下一步：

```text
Q length = 1
K/V length = 1002
```

此时每一步计算量相对小，但必须读取历史 KV Cache。

所以 decode 常常表现为：

> **memory-bandwidth-bound。**

Memory-bandwidth-bound 表示主要受显存带宽限制；大 batch、长上下文或不同模型也可能转成计算或通信受限，不能把这一判断当作所有 decode 的定律。Serving throughput 是单位时间服务完成的工作量。

把 1000 缩小到 3，可以逐步检查“输出”和“状态”为什么错开一位。设输入为 `[A,B,C]`，随后采样得到 D、E、EOS（End of Sequence，序列结束符）：

| 一次前向 | 本轮输入 | 前向结束后的有效 KV | 本轮新采样输出 |
|---|---|---|---|
| Prefill | A、B、C | A、B、C，共 3 个位置 | D，尚无 D 的 KV |
| Decode 1 | D | A、B、C、D，共 4 个位置 | E，尚无 E 的 KV |
| Decode 2 | E | A、B、C、D、E，共 5 个位置 | EOS，按停止规则结束 |

因此生成 $N\ge1$ 个输出 token，普通路径通常是一次完整 prefill 加 $N-1$ 次 decode，末尾停止 token 不必再喂回模型。CPU 运行时选择请求并准备位置和槽位；GPU 依序执行各层、写新 KV、产生 logits 并完成采样（具体采样也可能在 CPU）。采样结果就绪之后，才有下一步的实际输入。当前层临时 Q 和中间激活在最后一个消费者完成后可复用；各层历史 KV 要跨轮保存，直到请求不再使用且设备访问完成。流式发送结果与 GPU 完成是不同事件，第 20 章会细分回收条件。

<a id="s1-kv-cache为什么一个缓存能成为系统核心"></a>

### KV Cache：为什么一个“缓存”能成为系统核心？


Attention：

$$
Attention(Q,K,V)=softmax\left(\frac{QK^T}{\sqrt d}\right)V
$$

这里省略了 batch 和 head 维。对一个头，$Q$ 为 `[n_q,d_h]`，$K,V$ 为 `[n_k,d_h]`；$n_q$ 是新查询数，$n_k$ 是可供查询的历史加当前位置数，式中的 $d=d_h$。$K^T$ 转置后为 `[d_h,n_k]`，所以 $QK^T$ 是 `[n_q,n_k]` 的匹配分数；softmax 沿每行的 key 维归一化，乘 $V$ 后得到 `[n_q,d_h]`。数值本身无物理单位，元素数量乘 dtype 的字节数才是存储容量。

因果场景还要加 mask $M$：$P=\operatorname{softmax}(QK^T/\sqrt{d_h}+M)$。允许访问的位置取 $M_{ij}=0$，未来或无效位置取 $-\infty$，使其指数为零。若 Q/K 各分量近似独立、零均值、方差为 1，点积的 $d_h$ 项相加后方差约为 $d_h$，除以 $\sqrt{d_h}$ 将方差拉回约 1，避免维度增长时 softmax 过度尖锐。这是尺度设计的直觉假设，不是说实际训练后的分量一定独立。

可以手算一次单头查询。取 $d_h=2$，$q=[\sqrt2,0]$，三行 K 分别为 $[\ln2,0],[0,1],[0,-1]$，三行 V 分别为 $[1,0],[0,2],[2,2]$。此查询可见全部三行：

$$
\frac{qK^T}{\sqrt2}=[\ln2,0,0],\quad
P=\frac{[2,1,1]}{2+1+1}=[1/2,1/4,1/4],
$$
$$PV=\tfrac12[1,0]+\tfrac14[0,2]+\tfrac14[2,2]=[1,1].$$

若第三个位置是未来位置，它必须被屏蔽，概率变成 `[2/3,1/3,0]`，结果变成 `[2/3,2/3]`。由此可见，mask 是计算语义的一部分；把多条请求拼在一个张量中，不能让它们互相读取。实际融合注意力内核可以不把整个分数矩阵写入显存，但仍须实现相同的可见关系和归一化。

对于固定权重、固定位置规则的因果 Transformer，历史位置只能读取它自己及之前的输入。因此在序列末尾追加一个新 token，不会改变旧位置原来可见的前缀，也就不需要重算旧位置在各层的 K/V。

例如已经处理 `[A,B]` 并预测出 C，下一次前向只把 C 作为新输入，为它计算 Q/K/V。C 的 Q 读取 A、B 的缓存 K/V 以及 C 自己的新 K/V，得到当前位置的输出；旧 A、B 的 Query 不需要再次输出，因此通常只缓存 K/V。节省的是旧位置的重复前向，新的 Query 对历史的读取与加权计算仍然存在。若权重或位置语义改变，这个复用前提需要重新检查，第 20 章会解释失效情形。

所以保存：

```text
token 1 → K1,V1
token 2 → K2,V2
...
token t → Kt,Vt
```

这就是 KV Cache。

一个粗略的每 token KV Cache 大小公式：

$$
\text{bytes/token}
=
2\times L\times H_{kv}\times d_h\times \text{bytes(dtype)}
$$

其中：

- `2`：K 与 V；
- $L$：Transformer 层数；
- $H_{kv}$：KV heads 数；
- $d_h$：head dimension。

更具体地，一层一个位置的 K 有 $H_{kv}d_h$ 个数，V 也一样；乘两份、再乘 $L$ 层，得到元素数。FP16/BF16 每个元素 2 字节，故最后乘 $b=\text{bytes(dtype)}$，单位为 byte/元素。完整缓存长度 $S$ 的逻辑 K、V 各可写成 `[L,B,H_kv,S,d_h]`，未共享、未分片时总量为 $B S\times2LH_{kv}d_hb$ 字节；物理布局可以不同。该公式假设所有层使用相同配置，不包含量化尺度、页尾浪费或潜在的 KV 复制。

例如一个仅作直觉演示的 MHA 配置：

```text
32 layers
32 KV heads
head_dim = 128
FP16 = 2 bytes
```

则：

$$
2\times32\times32\times128\times2
=524288\text{ bytes}
$$

约等于：

> **512 KiB / token**。

2000 token 占 $2000\times512/1024^2=0.9765625$ GiB KV Cache。这里 KiB、MiB、GiB 分别是 $2^{10},2^{20},2^{30}$ 字节，不能与十进制 GB 混算。

现代 GQA/MQA 会明显降低这个数字，但它仍然可能成为 serving 中最大的动态显存消费者之一。

<a id="s1-为什么-kv-cache-会产生内存碎片"></a>

### 为什么 KV Cache 会产生“内存碎片”？


真实 serving 中请求长度不同：

```text
A: 700 tokens
B: 14000 tokens
C: 1200 tokens
D: finished
E: just arrived
```

输出长度在开始时通常又不知道。

如果提前给每个请求预留最大长度：

```text
Request A: [used][unused..............]
Request B: [used........][unused......]
```

会浪费很多显存。

如果不断 malloc/free 不同大小区域，又可能出现：

```text
used | hole | used | small hole | used
```

虽然空闲总量够，但找不到足够大的连续区域。

这就是碎片问题。

vLLM 是一个模型推理引擎，PagedAttention 是其提出的分页 KV 管理与访问方法。它借鉴操作系统的 virtual memory（虚拟内存）与 paging（分页）思路。

---


<a id="s1-virtual-memory-与-paging为什么-vllm-会借鉴操作系统"></a>

### Virtual Memory 与 Paging：为什么 vLLM 会借鉴操作系统？


操作系统希望进程看到：

```text
Virtual address
0 1 2 3 4 5 6 ...
```

但物理内存可以是：

```text
Physical page 7
Physical page 2
Physical page 91
...
```

中间通过 page table 映射：

```text
Virtual Page 0 → Physical Page 7
Virtual Page 1 → Physical Page 2
Virtual Page 2 → Physical Page 91
```

因此：

> **逻辑连续 ≠ 物理连续。**

PagedAttention 把 KV Cache 也拆成固定大小 block：

```text
Logical KV Block
       ↓ block table
Physical KV Block
```

这让请求可以按需增长，而不需要拥有一块连续的巨大显存。

这个类比有明确边界：KV block table 通常由推理运行时管理，attention kernel 用它查找 GPU 显存中的块，并非每次读取都触发操作系统缺页或磁盘 I/O。分页是“放在哪里、怎样找到”的问题，前缀缓存是“能否复用已经算过的值”的问题；前者不要求两个请求输入相同，后者要求状态身份相容。

<a id="s1-internal-fragmentation-与-external-fragmentation"></a>

### Internal Fragmentation 与 External Fragmentation


这是读 PagedAttention 必须区分的两个词。

<a id="s1-internal-fragmentation"></a>

##### Internal Fragmentation

已经分配了一块内存，但里面没有完全使用。

例如 block 容量 16 token：

```text
[10 tokens used][6 slots empty]
```

这 6 个 slot 是块内部浪费。

<a id="s1-external-fragmentation"></a>

##### External Fragmentation

空闲内存存在，但被分散在很多小洞中：

```text
used | free | used | free | used
```

没有一块足够大的连续区域。

固定大小 page/block 可以显著缓解外部碎片。

<a id="s1-copy-on-write-为什么会出现在-llm-serving"></a>

### Copy-on-Write 为什么会出现在 LLM Serving？


假设同一个 prompt 要采样 4 个回答：

```text
Prompt
  ├── Answer A
  ├── Answer B
  ├── Answer C
  └── Answer D
```

Prompt 的 KV Cache 完全相同。

没必要复制 4 份：

```text
共享 prompt blocks
```

当不同回答开始分叉，已写好的完整前缀块仍可只读共享。若最后一个共享块尚未填满，新 token 要写进这个块，直接写入会使其他分支也看到变化。这时先为写入方分配私有块，复制已有有效位置，再写入它的新 token，称为 Copy-on-Write（写时复制）。

例如块能放 4 个位置，当前共享尾块有 3 个位置；A、B 生成不同的第 4 个 token，就不能继续写同一尾块。若前缀刚好填满完整块，新 token 直接进入各分支的新块即可，无须复制已经封满的前缀块。实际引擎是否共享部分尾块会影响复制时机。

它同样源自操作系统进程 `fork()` 的经典设计思想。

---


<a id="s1-prefix-cache-与-radix-tree-的直觉"></a>

### Prefix Cache 与 Radix Tree 的直觉


假设很多请求都包含：

```text
You are a helpful assistant...
```

如果这段 prefix 的 KV 已经算过，就可以直接复用。

但真实请求共享关系可能是多层的：

```text
                System Prompt
                /           \
          Conversation A   Few-shot Prompt
             /    \              /   \
           A1     A2            Q1    Q2
```

若只用完整 prompt 作为一个哈希键，难以直接查找最长可复用前缀；也可以设计按块哈希和前缀链来实现复用，并不是只有树才能做到。

Radix Tree（基数树）将公共前缀合并为共享路径，因而自然表达：

> **最长公共前缀和树状共享关系。实际可复用粒度仍受 KV 块大小与实现约束。**

这就是 RadixAttention 的核心数据结构基础。

## 2. 采样、自回归依赖与推测解码


<a id="s2-logits-不是最终-token"></a>

### Logits 不是最终 token

模型输出词表 logits，经过规定的温度、屏蔽、截断或其他处理后形成采样分布。Greedy、top-k、top-p 是不同的决策或分布变换。返回的 logprob 需要说明对应原始模型还是处理后的分布。

停止 token、最大长度、约束解码和重复惩罚改变生成过程。强化学习（RL）训练若需要行为策略概率，必须匹配实际采样语义，而不是仅保存任意一份模型 logits。

<a id="s2-用三个-token-看懂采样"></a>

#### 用三个 token 看懂采样

设 logits 为 $[\ln 6,\ln 3,\ln 1]$，在温度 T=1 时 softmax 得到概率 `[0.6,0.3,0.1]`。这里 ln 是自然对数，logprob 就是所选 token 概率的自然对数，例如第一个 token 为 $\ln 0.6≈-0.511$。

Logit $z_i$ 是第 $i$ 个词表项的实数分数，可以为负，也不要求加起来为 1。温度 $T>0$ 无量纲，对词表中每项有

$$p_i=\frac{\exp(z_i/T-m)}{\sum_j\exp(z_j/T-m)},\qquad m=\max_j(z_j/T).$$

减去相同的 $m$ 不改变比值，却能防止指数溢出。本例不减最大值也容易手算：指数是 6、3、1，总和 10，逐项除以 10 即得概率。采样器可抽 $u\in[0,1)$ 的均匀随机数，用累计区间 `[0,0.6)`、`[0.6,0.9)`、`[0.9,1)` 决定输出；例如 $u=0.72$ 选第二项。概率 0.3 表示多次试验的选择频率，不是给当前 token 打“30 分”。

- Greedy（贪心）总选最大概率的第一个 token。
- 随机采样按 0.6/0.3/0.1 的概率选择，单次结果不一定是第一个。
- Top-k 只保留概率最高的 k 个；k=2 时重新归一化为 `[2/3,1/3,0]`。
- Top-p 保留按概率降序排列、累计概率达到阈值的最小前缀集合；阈值 0.8 时，本例也保留前两个。
- 温度先将 logits 除以 T；T=2 时概率与 `[√6,√3,1]` 成比例，比 T=1 更平缓。T=0 通常是接口的贪心约定，不能直接代入除法。

多个处理组合时必须规定顺序。Mask 可将不允许的 token 概率置零；约束解码依语法等规则选择允许集合；停止 token 用于结束生成。重复惩罚会依据已有输出调整 logits，其具体公式随实现而异。

本例 top-k 之后第一个 token 的 logprob 为 $\ln(2/3)≈-0.405$，与原模型的 -0.511 不同。后面的强化学习（RL）章节需要区分它们，才能知道数据究竟由哪个分布产生。

贪心的行为分布在选中项上为 1、其余为 0，但接口可能仍返回原模型的 logprob；“返回了概率”不等于“返回了行为概率”。另外，允许集合不能为空：若所有 logits 都被屏蔽成 $-\infty$，归一化分母为零，需要报告约束失败或使用明确定义的恢复策略，不能默默当作均匀分布。

<a id="s2-自回归的顺序依赖"></a>

### 自回归的顺序依赖

下一个 token 的输入包含上一步结果，因此普通生成存在逐步依赖。增加 batch 能让不同请求并行，但不会自动消除单请求输出步骤之间的依赖。

推测解码让较便宜的过程提出多个候选，再由目标模型验证。候选可以来自独立 draft 模型或其他机制；具体方法对训练、状态和概率校正的要求不同。

<a id="s2-精确采样校正的直觉"></a>

### 精确采样校正的直觉

在一种标准构造中，候选由 q（便宜的草稿分布）采样，目标分布为 p（希望最终保持的分布），对候选 token x 以 $\min(1,p(x)/q(x))$ 接受；拒绝时依据归一化的正残差 $(p-q)_+$ 采样。正残差表示对每个 token 取 max(p−q,0)，再除以所有正残差之和。q(x)=0 的候选不会被 q 提议；若 p=q，拒绝概率为零，无需进入残差分支。完整多步算法还需要正确处理前缀条件和额外 token。

这说明接受规则属于正确性证明的一部分。简单接受“目标模型也觉得可能”的 token，不能自动保证目标分布不变。Greedy 一致性与随机采样分布一致性也应分别验证。

逐项推导一次就能看出残差从哪里来。候选 $x$ 被提出且接受的总概率是 $q(x)\min(1,p(x)/q(x))=\min(p(x),q(x))$。所有候选的拒绝概率为

$$R=1-\sum_x\min(p(x),q(x))=\sum_x[p(x)-q(x)]_+.$$

若 $R>0$，拒绝后按 $r(x)=[p(x)-q(x)]_+/R$ 采样，最终落到 $x$ 的概率为

$$\min(p(x),q(x))+Rr(x)=\min(p(x),q(x))+[p(x)-q(x)]_+=p(x).$$

每一项都是无量纲概率。证明在固定前缀下成立，多步时在每个已接受前缀上重复应用，才得到目标的联合分布。它保证分布相同，不保证相同随机种子下逐字结果相同，也不消除浮点实现误差。构造依据见[原论文的精确采样算法](https://arxiv.org/abs/2211.17192)。

<a id="s2-性能与状态成本"></a>

### 性能与状态成本

设一次 draft 加验证耗时为 $T_d+T_v$，平均提交 k 个 token，则粗略成本为 $(T_d+T_v)/k$。它必须与相同负载和质量条件下的基线比较。接受率高不保证加速：draft 太慢、验证形状不合适或 batch 已很大，都可能削弱收益。

拒绝候选后，KV 或递推状态需要回到接受前缀对应的状态。对于原地更新的有限状态模型，回滚方式尤其需要设计。还要核对随机数、位置和输出计数。

<a id="s2-三token词表的精确接受与拒绝推演"></a>

### 三token词表的精确接受与拒绝推演

用词表{a,b,c}，目标分布p=[0.5,0.3,0.2]，draft分布q=[0.2,0.5,0.3]。这里p/q都是相同已接受前缀下、规定采样处理之后的分布。

| 候选 | 被q提议的概率 | 条件接受概率min(1,p/q) | 提议且接受的概率 |
|---|---:|---:|---:|
| a | 0.2 | 1 | 0.2 |
| b | 0.5 | 0.6 | 0.3 |
| c | 0.3 | 2/3 | 0.2 |

总接受概率0.7，总拒绝概率0.3。正残差(p−q)+=[0.3,0,0]，归一化后拒绝分支必选a。因此最终输出概率为a:0.2+0.3=0.5，b:0.3，c:0.2，恰好恢复p。

若拒绝时直接重新按p采样，最终质量则为[0.2,0.3,0.2]+0.3p=[0.35,0.39,0.26]，已经改变目标分布。这个反例说明“再问目标模型一次”不能替代正确残差校正。

<a id="s2-多步候选的状态如何提交"></a>

### 多步候选的状态如何提交

设draft提出[x1,x2,x3]。目标模型可以在这些候选前缀上计算相应验证分布，但只有前面的候选被接受，后续分布才对应真实已提交前缀。

并行验证不违反自回归依赖：候选已经暂时给出了未来输入，目标模型只是一次算出“假设这些输入成立，各位置会给什么分布”。设完整前缀为 C，验证 $x_1$ 要用 $p(\cdot\mid C)$，验证 $x_2$ 要用 $p(\cdot\mid C,x_1)$，依此类推；输入 $x_1$ 所产生的 logits 预测的是 $x_2$，不能错拿来验证 $x_1$。运行时可复用已有首个分布，也可连同尚未写 KV 的前缀末 token 一起前向，具体输入行数因实现而异。

假设x1被接受、x2被拒绝并校正为y2，则提交输出[x1,y2]，x3作废。目标侧保留与原前缀+x1对应的有效KV；为x2/x3形成的候选后缀不能继续当作真实上下文。y2通常尚未经过下一次forward，其KV还未计算。若采用不同的fused执行，仍要满足同一逻辑长度与状态。

若所有候选都接受，经典方案还可从目标模型的最后一个分布采样额外token。这个额外token与普通decode刚采样出的token一样，不能因为已经输出就认为其KV已写入。分叉、拒绝与回滚因此要同时维护输出长度和已计算KV长度。

<a id="s2-一组明确假设的成本比较"></a>

### 一组明确假设的成本比较

假设普通目标decode每步10 ms；每轮draft耗时4 ms，目标验证12 ms，其他成本忽略。若一轮平均提交2个token，摊销成本8 ms/token，相对该基线为1.25倍速度；若平均只提交1个，则16 ms/token，反而更慢。

用单位检查：$T_d,T_v$ 是 ms/轮，$k$ 是 token/轮，相除是 ms/token。本例要胜过 10 ms/token，须有 $16/k<10$，即 $k>1.6$。如果理想化地假定每个候选在前面均已接受时的条件接受率都是 $\alpha$，一轮提出 $\gamma$ 个候选，且没有 EOS 或长度截断，则经典方案平均提交 $k=1+\alpha+\cdots+\alpha^\gamma$；第 $j+1$ 个提交位置存在，需要前 $j$ 个候选全部接受。真实接受率随前缀变化，应直接统计每轮提交长度，不能把单个平均接受率机械代入。

这里的平均提交长度包含该算法允许的额外token；接受率、候选数与平均提交长度不是同一个统计量。服务负载、验证batch、draft位置变化后，所有时间都应重新测量。本例没有声称任何具体模型有此收益。

验证：[接受概率与成本脚本](<../examples/training_rl_walkthroughs.py>)；状态管理见[KV推演](<20_KV容量分页与复用.md#s1-数值展开-kv分页前缀共享分叉与取消>)，调度背景见[推理运行时演进史](<../appendices/serving/推理运行时演进史.md>)。

<a id="s2-演进边界"></a>

### 演进边界

普通逐 token 生成简单但受依赖限制；多候选验证增加并行工作，代价是候选成本与状态管理；更紧密集成的预测结构减少某些开销，又引入模型训练或部署条件。应该同时记录接受长度、额外工作、端到端延迟和分布验证。

参考：[Fast Inference from Transformers via Speculative Decoding](https://arxiv.org/abs/2211.17192)。实现语义参见[SGLang 请求与采样](<../appendices/source/sglang/04_interfaces_and_models/01_api_request_and_sampling.md>)。

## 3. 结束原因也是生成结果的一部分

相同的可见文本，可能来自模型主动生成 EOS，也可能来自达到长度上限、命中停止字符串、客户端取消或服务超时。在线服务也许都能显示一段文字，训练却必须知道是哪一种结束。模型是否选择停止，与系统不再允许它继续，是不同的事件。

例如回答 token 为 `[B,C,EOS]`，用户界面只展示 B、C。如果训练目标包含终止动作，就需要保存 EOS 的 token ID 和概率；若引擎把 EOS 从展示结果中移除，数据整理不能仅凭返回文本重新分词重建动作序列。停止字符串也可能跨越多个 token，展示文本与实际采样记录更可能不同。

一个适合交给训练的生成结果，应保留输入 token、实际采样 token、每个动作对应的概率定义、结束原因，以及所用策略与采样配置。文本可以作为检查与奖励输入，但不能成为动作身份的唯一依据。

以输入 `[A]`、输出 `[B,C,EOS]` 为例，记录的三份概率应依次对应 $P(B\mid A)$、$P(C\mid A,B)$、$P(EOS\mid A,B,C)$，数组长度都是 3。最后一份概率来自消费 C 的前向，而非消费 EOS。若因输出上限 2 而停在 `[B,C]`，就没有第三次采样，也不能补一个虚构 EOS 概率。客户端取消则是服务事件，甚至可能发生在 GPU 已采样、结果尚未交付之时，需要按协议区分“已生成”和“已交付”。

达到最大长度时，是否把最后位置当成任务终点，由训练目标决定；有价值函数的算法还可能需要对未结束状态估值。先保留真实结束原因，后续才有条件作出正确处理。第 25 章会解释终止与截断怎样影响回报，第 28 章将同一问题扩展到多轮环境。
