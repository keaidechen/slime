# 负载、状态与资源需求：同一个模型怎样形成不同的系统

前置：[系统全景](系统全景与设计方法.md)。模型定义一次计算的结构；负载还规定工作何时到达、重复多少次、依赖谁、状态保留多久。选硬件或并行方案之前，需要把这些信息写成可复用的输入。

## 一个工作负载至少包含哪些信息

| 对象 | 必须区分的字段 | 影响什么 |
|---|---|---|
| 在线生成 | 到达时刻、输入／输出长度、期限、取消 | 突发、排队、KV 峰值与尾延迟 |
| 多轮 Agent | 轮间依赖、工具时间、分支、复用间隔 | 模型调用数、环境与 KV 驻留 |
| 训练 | 长度、mask、数据混合、有效 batch、目标质量 | 实际计算、更新次数与收敛 |
| RL | 生成数、保留率、评分成本、行为版本、消费速率 | 有效供给与样本陈旧度 |
| 实时媒体 | 字节／帧／块、到达节奏、首播放与连续性 | 编码、网络与分阶段背压 |

输入与输出长度应保留联合分布。前缀复用还依赖模型／adapter 身份及位置规则；“文本相同”不能单独证明 KV 可共享。在线生成的压测需固定到达方式，详见[开环、闭环与容量](../10_Inference_Serving/排队长尾与容量规划.md)。

## 一个可重复使用的教学模型

下面与[推理设计案例](../10_Inference_Serving/推理并行方案设计.md)复用模型容量和请求长度，所有数值均为教学输入：

| 项目 | 固定值 |
|---|---|
| 参数与权重 | 80 亿参数，BF16 共 16 GB，约 14.90 GiB |
| KV 结构 | 32 层、8 个 KV 头、头维 128、K/V 各 BF16 |
| 短请求 | 输入 1024、输出 256 token |
| 长请求 | 输入 8192、输出 512 token |
| 到达 | 两类各 1 请求／秒，合计 2 请求／秒 |

模型名称不绑定实际 checkpoint。未分片、未共享、未量化时，每个历史 token 的 KV 字节数为

$$b_{\mathrm{KV}}=2\times32\times8\times128\times2=131072\ \mathrm{B}=128\ \mathrm{KiB}.$$

保守按输入加全部输出预留，短请求需 160 MiB，长请求需 1088 MiB。预留量是容量上界；最后采出的 token 尚未产生 KV，不能把预留位置当作已提交状态。页对齐、工作区、共享与分片须另计，见[推理内存系统](../10_Inference_Serving/推理内存系统.md)。

## 从每任务需求换算成每秒需求

两类各 1 请求／秒时，新输入为 9216 token/s，输出为 768 token/s。这两种 token 不能直接相加后乘一个固定“每 token 成本”：Prefill 与 Decode 的矩阵形状、历史访问和批内复用不同。

设任务到达率为 $\lambda$，第 $r$ 类资源每项任务平均消耗 $d_r$，则平均需求率为 $\lambda E[d_r]$。例如若给定每项任务平均需要 0.6 GPU·秒，则 2 项／秒要求平均 1.2 张 GPU 的有效服务能力。这个资源时间必须已经包含相应批处理分摊，不能把一个 batch 的整段耗时重复计给每个请求。

需求低于能力只是稳态可行的必要检查。长尾、突发、调度和阶段配比仍可能破坏时限；多阶段系统需要对每个阶段分别检查。先估算瓶颈，再进入[训练](../09_Training_Systems/训练并行方案设计.md)或[推理](../10_Inference_Serving/推理并行方案设计.md)的完整方案比较。

## 状态容量取决于占用量和驻留时间的联合分布

稳定系统中，平均在途数量满足 Little 定律 $\bar N=\lambda E[T]$，其中 $T$ 必须与所统计系统的进入／退出边界一致。包括排队的时间对应包括排队的数量；仅统计持有 KV 的请求，就只计算 KV 驻留时间。

对请求的状态轨迹 $M(t)$，平均占用可写成

$$\bar M_{\mathrm{total}}=\lambda E\left[\int_0^T M(t)\,dt\right].$$

若每条请求在整个驻留期预留固定容量 $M$，则为 $\lambda E[MT]$。它通常不等于 $\lambda E[M]E[T]$，因为长请求往往既占空间又停留更久。此关系用于稳定长期平均；共享前缀需按唯一物理对象核算，不能逐请求重复累加。

继续用上面的预留量，另外假设短／长请求持有预留空间 2／8 秒。这是本节的驻留模型，不是案例引擎的执行性能。每类各到达 1 请求／秒，得到：

| 类别 | 平均驻留请求数 | 每条预留 | 平均总预留 |
|---|---:|---:|---:|
| 短 | $1\times2=2$ | 0.15625 GiB | 0.3125 GiB |
| 长 | $1\times8=8$ | 1.0625 GiB | 8.5 GiB |
| 合计 | 10 | — | **8.8125 GiB** |

若错误地把平均单请求预留 0.609375 GiB 乘平均在途数量 10，会得到 6.09375 GiB。漏掉的是请求大小与驻留时间的相关性。对给定在途队列直接累加物理占用，才能进一步得到瞬时峰值。

## 相同平均到达率可以产生不同等待

一个教学服务台每条请求执行 1 秒，FCFS 串行处理。观察提交窗口 $[0,4)$：

| 到达方式 | 到达时刻／秒 | 等待时间／秒 | 最大等待 |
|---|---|---|---:|
| 均匀 | 0、1、2、3 | 0、0、0、0 | 0 |
| 突发 | 0、0、0、0 | 0、1、2、3 | 3 |

两者都提交四条请求，平均提交率相同。若响应必须在到达后 2 秒内完成，均匀到达全部达标，突发只有前两条达标。这个串行模型用于说明到达顺序的作用；真实连续批处理需要换入 batch 执行时间和 KV 限制。

做容量规划时还应看短时间窗口里的需求：扩容完成前积压多少工作，积压期间状态能否放下，新容量要多久才能排空。平均负载低于峰值能力不能回答这些问题。

## 缓存命中率需要对应节省的工作

假设短请求无命中，长请求命中 6144 个输入 token，则实际新计算输入从 9216 降到 3072 token/s；按请求计的命中率只是 50%。输出仍为 768 token/s。长请求仍需要合法的完整上下文状态，且新增查询还要读取缓存历史，因此 Prefill 的全部成本不一定按新 token 数同比下降。

若长请求都共享同一前缀，本实例的物理 KV 可共享；若命中发生在 Prefill 实例，而 Decode 实例尚无副本，交接仍可能传完整 KV。分别记录命中的请求数、token 数、实际省下的工作和状态移动量，详见 [PD 交接](../10_Inference_Serving/案例_Prefill-Decode分离.md)。

## 多轮、训练与 RL 怎样使用同一语言

Agent 任务的请求率取决于每项任务产生多少次调用；工具只执行很短时间，环境仍可能跨轮驻留。分支增加调用数，取消后未及时停止的分支继续消耗资源。资源时间的进一步核算见[环境容量与生命周期](../11_RL_Systems/Agent环境容量与生命周期.md)。

训练中，相同有效 token 数也可能有不同 Attention 工作量、padding、重算和更新次数。先写清目标与有效分母，再估算供给与执行成本，见[训练数据管线](../09_Training_Systems/数据管线与训练演进.md)。

RL 的阶段需求还应包含被过滤、过期和失败的生成。若每秒生成 10 组、按组有效率 60%，learner 最多得到 6 组／秒；若其消费仅 4 组／秒，还需控制额外积压。有效率随策略和题目变化，固定配比可能不再适合。完整契约见[奖励与质量闭环](../11_RL_Systems/奖励评估与质量闭环.md)。

## 用记录校准需求

一份最小任务记录应能连接：任务／请求／attempt 身份、模型配置、到达与接纳时刻、各阶段起止、实际输入输出、状态占用、结束原因及质量结果。记录原始分布，再生成平均值与分位数；未完成和取消任务单列。

将估算分成三项：确定的形状与字节数、需要测量的执行参数、需要随流量更新的分布。变化发生后只替换相应输入，就能判断原方案是否仍可行。验证方法见[证据与因果](../12_Performance_Reliability/证据与因果.md)。
