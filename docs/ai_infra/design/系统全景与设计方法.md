# 系统全景与设计方法：从一次请求看到整个系统

AI Infra 把任务变成可执行的模型工作，并组织完成任务所需的设备、数据和状态。设计之前先说明“完成”的含义：聊天要在时限内返回回答，代码 Agent 要交付通过检查的结果，训练要在资源预算内达到约定质量。三个目标可能使用同一模型，却需要不同的系统。

本文先建立地图。张量、梯度、GPU 与并行的细节由后面的[机制主线](../guides/系统阅读路线.md)逐步展开。

## 一次生成经过哪些角色

~~~mermaid
flowchart TD
    A["应用：任务、上下文与期限"] --> B["服务入口：协议、配额与请求身份"]
    B --> C["路由：选择一个可接纳的实例"]
    C --> D["实例调度：队列、批次与状态容量"]
    D --> E["CPU 运行时：准备输入、提交与处理结果"]
    E --> F["加速器：算子、权重读取与 KV 读写"]
    F --> E
    E --> G["输出处理与流式连接"]
    G --> A
    A --> H["工具环境：执行动作并保存结果"]
    H --> A
~~~

**实例**是能完成一次模型调用的一组执行资源，可以包含一张或多张卡。**副本**是另一个能独立接收请求的实例。路由选择实例，实例内部的调度器选择当前要执行的工作；作业调度器还负责为实例分配设备。这几个调度层的对象与时间尺度不同。

具体软件可以合并进程、拆出分词前端，或把编码、Prefill 与 Decode 放在不同资源池。图表示职责，不规定进程数量。固定实现可继续看 [SGLang 请求路径](../13_Source_Analysis/sglang/01_foundations/02_process_topology_and_request_path.md)。

模型先处理已知输入，称为 Prefill；然后逐步生成，称为 Decode。KV 是后续注意力会复用的历史表示。刚采样出的 token 在下一次前向中才产生自己的 KV，因此输出数量与已提交 KV 长度不总同步。请求完成后，可复用的前缀仍可能保留，资源回收必须考虑其他请求及设备上的在途访问。

工具调用又增加一层循环：一次生成产生动作，工具返回观察，应用据此发起下一次生成。模型请求结束、工具执行成功、整个任务通过检查，是三个不同的完成点。

## 同一份权重有不同的数据路径

~~~mermaid
flowchart LR
    S["持久存储：权重文件"] -->|"启动或换权时加载"| H["主存与加载缓冲"]
    H --> V["各设备显存：权重与状态"]
    V -->|"每次执行所需读取"| C["片上存储与计算单元"]
    C -->|"中间结果与新增状态"| V
    V <-->|"分片之间交换数据"| R["其他设备显存"]
~~~

权重常驻显存减少了反复加载文件的成本，计算时仍要读取所需权重。批处理让多个 token 复用一次权重读取，缓存减少重复计算，分片让多设备分别保存和计算一部分；它们改变的是不同层级的数据量与依赖。

实际路径还可能有设备直连、远端内存或分层缓存。判断优化时，要指出节省的是 SSD、主存、HBM 还是网络上的访问，并核对新增的本地缓冲与同步。基础推导见[局部性与数据移动](../00_Physical_Foundations/局部性与数据移动.md)。

## 训练与 RL 怎样接回这张图

训练把样本变成损失，通过反向传播产生梯度，再更新参数。前向激活、梯度、优化器历史和数据游标都有自己的生命周期；训练恢复需要取得相容的一组状态。

RL 将生成端与训练端连接起来：

~~~text
策略快照 → 生成与环境交互 → 奖励和样本筛选
                                  ↓
发布可服务的新快照 ← 参数更新 ← 有效训练样本
~~~

发布版本、生成时的行为版本和训练时使用的版本可能不同。数据流需要记录身份，吞吐需要按有效样本计算，质量需要独立评估。源码主线分别是 [Megatron 的更新](../13_Source_Analysis/megatron/README.md)与 [slime 的闭环](../13_Source_Analysis/slime/README.md)。

## 六个层次怎样相互约束

| 层次 | 向下提出什么要求 | 向上暴露什么限制 |
|---|---|---|
| 任务与产品 | 质量、期限、交互方式、成本上限 | 成功与失败如何判定 |
| 模型与负载 | 计算图、形状、请求分布、状态寿命 | 可接受精度、因果顺序、模型能力 |
| 训练／推理／RL 系统 | 切分、批处理、状态交接 | 排队、并行气泡、版本与恢复边界 |
| 算子、编译与运行时 | 布局、融合、执行依赖 | 可用内核、临时空间、提交成本 |
| 设备与存储 | 计算、容量、读写与持久化 | 算力、带宽、延迟、功率 |
| 互联与资源平台 | 放置、共享、数据交换 | 拓扑、配额、故障域、扩容时间 |

这些层次可以沿两个方向阅读：从任务向下推资源需求，从设备向上检查方案能否执行。观测与恢复横跨多层；一条慢请求可能在入口排队，也可能在 GPU 等待数据，不能由某一张利用率图独自解释。

## 四份账本连接需求与实现

每次设计记录以下四项，单位分别写清：

| 账本 | 要记录的量 | 容易遗漏的部分 |
|---|---|---|
| 工作 | FLOP、有效 token、调用／更新次数 | 重算、丢弃样本、失败重试 |
| 容量 | 每设备同时存活的字节 | 峰值、共享引用、临时双份状态 |
| 时间 | 操作耗时、先后依赖、排队与期限 | 冷启动、下游阻塞、故障恢复 |
| 产出与成本 | 合格任务数、设备时间、总支出 | 空闲资源、未完成任务、质量变化 |

这四份账需要共同解释一个选择。例如缩小 KV 可以增加并发，但并发增加也会拉长一步执行时间；增加副本可以减少排队，却会复制权重并分散前缀缓存。最后比较的仍是原来的质量和期限目标。

## 从一个设计题走到可验证结论

1. **固定任务合同。** 输入分布、目标质量、延迟／期限、失败口径和可用资源必须明确。
2. **展开执行图。** 画出计算、存储与网络阶段，标记谁拥有状态、什么事件后可以消费或释放。
3. **排除不可行方案。** 核对每设备峰值容量、稳定供给能力和无法缩短的依赖链。
4. **比较可行候选。** 对同一工作负载算时间与成本，列出每项优化减少和增加的工作。
5. **改变关键条件。** 提高到达率、延长上下文、降低命中率或减慢链路，找出选择翻转的位置。
6. **取得证据再定配置。** 用数值核对、固定源码和真实测量依次校准；保留预测与实测的差值。

单个可重叠阶段的时间可先用计算、访存和通信的资源下界筛选，但串行阶段需要沿依赖相加，共享带宽也不能重复分配。峰值算力与总显存足够，只证明通过了一部分检查。完整时间模型见[性能与关键路径](../12_Performance_Reliability/00_concepts.md)。

## 自测：四卡实例还是四个副本

假设模型和单条请求的状态均可放入一张卡。四张卡协作使一个请求更快，同时每层需要通信；四个独立实例则可以同时处理不同请求。只有一句“有四张卡”，无法确定方案。还需要单请求时限、请求到达和长度分布、单卡与四卡执行时间、每实例 KV 容量，以及缓存能否复用。

如果比较过程中偷偷减少输出长度、改变采样或放宽质量门槛，就已经换了任务合同。若选择依赖某个尚未测量的通信时间，应把它列为待校准参数，并给出允许的范围。
