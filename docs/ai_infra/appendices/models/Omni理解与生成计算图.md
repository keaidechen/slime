# Omni 理解与生成计算图

[表示篇](<音视频表示与时间对齐.md>)已经算出 10 秒音频可以形成 `[250,1024]` 的特征。现在把特征接到实际工作上：谁产生条件，谁维护历史，何时能交付结果？这里的“计算图”表示数据依赖，不要求每个框都是独立服务。

## 案例 A：从声音到流式语音回答

采用一条教学路径：输入音频编码器 → 理解骨干 → 语音生成器 → 波形解码器。理解骨干在部分文献中叫 Thinker，语音生成器叫 Talker；这是角色名称，不是所有模型共同的接口规范。

```text
PCM 波形 → mel → 音频编码器 → 媒体特征 → 投影/输入组合
                                                ↓
文本上下文 ─────────────────────────────────→ 理解骨干 → 文本结果
                                                ↓ 条件
                                         语音生成器 → codec 帧
                                                           ↓
                                                     波形解码器 → 音频块
```

“条件”指控制生成内容的输入，可以包含文本、媒体特征、说话人表示或特定隐藏状态；究竟传哪些张量由模型定义。不能只看到 Thinker/Talker 命名，就假定下游一定读取上游最后一层全部 hidden states。

Qwen3-Omni v1 的 Talker 使用文本及多模态条件，以自回归和多 token 预测协作生成 codec，再用因果卷积网络完成波形解码。这是一个具体分解，不能据此把所有语音解码器都写成扩散模型。[技术报告](https://arxiv.org/html/2509.17765v1)

| 阶段 | 本例输入 → 输出 | 必须持续维护的状态 |
|---|---|---|
| 音频预处理 | 160000 采样点 → `[998,80]` | 增量窗口的重叠样本、时间戳 |
| 编码器与投影 | `[998,80]` → `[250,1024]` → 骨干宽度 | 若增量执行，保存模型要求的左侧上下文 |
| 理解骨干 | 250 媒体位置 + 128 文本位置 → 文本与生成条件 | 本例初始 KV 47.25 MiB，随后随生成增加 |
| 语音生成器 | 条件 + 历史 codec → `[帧数,8]` 索引 | 自回归历史、帧内预测状态、未消费条件 |
| 波形解码器 | 10 个 codec 帧 → 200 ms 波形 | 因果卷积缓存或模型规定的重叠区 |

这里只约定输出 codec 为 50 Hz、8 码本。若输出波形为单声道 24 kHz、PCM16，200 ms 音频块有 4800 采样点、9600 字节；不能沿用输入的 16 kHz 去解释它。发送的可能是压缩音频，网络负载还会不同。

## 因果性决定可以怎样分块

自回归（AR）表示当前输出依赖之前已经确定的输出。对于 codec `c[t,k]`，t 是时间帧，k 是码本。一个模型可以让每帧依赖历史帧，再用帧内小网络处理码本；另一个可以把 `(t,k)` 展成一条长序列。两者输出 shape 相同，关键路径却不同。

因果模块不能读取尚未到达的未来输入；带右侧预读（lookahead）的模块需要等待一部分未来。假设输入以 20 ms 片段到达，编码器每次还需 40 ms 右侧上下文，则忽略计算时长也有这部分等待。文件模式先拿到整段音频，不能用其测试结果证明实时因果路径成立。

波形解码也有边界状态。逐块重置卷积缓存可能产生接缝；有重叠区的算法必须按规定拼接，不能把重叠样本播放两次。最后一块不足 10 帧时，需记录有效采样数、padding 和结束信号。张量补齐到相同 shape 与实际音频时长是两回事。

## 案例 B：条件驱动的媒体生成

现在换成“依据文字与参考图生成 512×512 图像”。假定模型在空间压缩 8 倍、4 通道的 latent 上生成，初始状态 `[64,64,4]`。BF16 单份 latent 是 64 × 64 × 4 × 2 = 32768 字节，即 32 KiB。参考图若参与条件编码，其 resize/crop 与编码器版本也是条件身份的一部分。

```text
文字/参考图 → 条件编码器 → 固定条件 C ───────────┐
随机数种子 → 初始噪声 z₀ → 迭代更新 z₁ … z₂₀ ← 生成网络(zᵢ, 时间, C)
                                             ↓
                                       媒体解码器 → 图像 → 编码/发送
```

这里 `zᵢ` 的下标 i 只是执行顺序，不强行等同于某篇论文从 T 到 0 的扩散时间符号。每步更新整份 latent，不是给文本 KV 追加一个位置。生成网络可以预测噪声、速度或其他参数化量，调度器/数值求解器据此推进状态；不同目标的公式不可混用。[DDPM](https://arxiv.org/abs/2006.11239)的噪声例子已在[多模态与扩散计算](<多模态与扩散计算.md>)中展开。

若以 2×2 latent patch 做 Transformer 输入，位置数为 `(64/2)²=1024`；隐藏宽度 1152 时，仅一份 `[1024,1152]` BF16 隐藏张量就是 2.25 MiB。因此 latent 很小并不意味着模型峰值内存很小。还应数权重、Attention 中间量、残差、并行通信缓冲和解码器 workspace。[DiT](https://arxiv.org/abs/2212.09748)提供了在 latent patch 上使用 Transformer 的原始研究入口。

## 一个能手算的连续状态更新

为了只看清状态推进，取一维噪声 `z₀=-1`、目标数据 `z₁=2`，定义插值 `z(t)=(1-t)z₀+t z₁`，t 从 0 到 1。沿该路径的速度是 3。用 4 步 Euler 更新、每步 Δt=0.25：

\[
z_{i+1}=z_i+0.25\times3,
\quad -1\to-0.25\to0.5\to1.25\to2.
\]

真实模型需要从数据学习条件速度场；本例直接给出正确速度，只用于核对状态和恢复，不能生成真实图像。Flow Matching 学习向量场的目标与 DDPM 噪声预测目标不同。[原始论文](https://arxiv.org/abs/2210.02747)

第 2 步后保存 `z=0.5` 和已完成步数 2，再执行两步可恢复到 2。若仅保存初始 seed，无法从第 2 步继续：还需当前 latent、时间网格与求解器状态；随机求解器还要保存当前 RNG 状态。多步求解器可能额外依赖之前的导数估计。

## 两条计算图的状态对照

| 问题 | 案例 A：语音回答 | 案例 B：图像生成 |
|---|---|---|
| 推进单位 | 文本 token、codec 帧、可播放音频块 | 对整份 latent 的一次迭代 |
| 不变部分 | 已提交的输入与可复用条件 | 文本/参考图条件，前提是配置相同 |
| 变化部分 | KV、生成历史、播放进度 | latent、步数、求解器和随机数状态 |
| 中途结果 | 可能已经被用户听到 | 可做预览，但未必符合最终质量条件 |
| 取消后果 | 丢弃未播放部分，并处理已听前缀 | 丢弃未完成结果或标成明确的预览 |

本例媒体生成的固定时间预算为：条件编码 50 ms + 20 步 × 40 ms + 媒体解码 30 ms + 传输 20 ms = 900 ms。40 ms 是**包含本例所有条件引导分支**的一次完整步骤成本；不能再把分支成本重复加一遍。串行预算没有包含排队，优化篇再讨论重叠与近似。

## 自测

**为什么给图像生成配置 20 个文本 decode step 的缓存预算不够？** 图像步骤更新完整 latent，涉及的张量与中间状态不同；应按模型形状和求解器生命周期核算，不能按文本输出长度替代。

**首个 codec 帧出现是否就能播放？** 还取决于波形解码器需要多少上下文、攒了多少帧、传输和客户端缓冲。接下来读[流式生成与会话状态](<../serving/Omni流式生成与会话状态.md>)，把计算完成与用户体验连起来。
