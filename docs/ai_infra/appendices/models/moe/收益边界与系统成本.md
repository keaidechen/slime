# MoE 为什么省计算却未必省时间

MoE 的效率不能由“每 token 激活多少参数”单独判断。重排、All-to-All、专家矩阵形状和慢 rank 都可能抵消计算节省。本篇将这些成本连到可观察的失效信号，并说明吞吐与质量结论的边界。

## 从逻辑激活到实际执行

先固定同一个模型、路由规则和待处理 token 集合，只改变系统怎样执行。对一个 routed-expert 层，设整个 EP 组本轮共有 $B$ 个有效 token、$E$ 个逻辑专家，每个 token 选择 $K$ 个不同专家。用 $a_{ie}\in\{0,1\}$ 表示 token $i$ 是否分派给专家 $e$，则

$$
m_e=\sum_i a_{ie},\qquad \sum_e m_e=BK,
\qquad U=\{e:m_e>0\}.
$$

这里假设不丢 token、不重复选择同一逻辑专家；共享专家和 dense 路径另算。$BK$ 是分派总数，$m_e$ 是专家矩阵的有效行数，$U$ 是批内被访问的专家并集。它们回答不同问题：分派总数决定理想工作量，分布决定矩阵形状和负载，并集影响本轮需要访问多少不同权重。

以“各 token 独立、均匀选择 $K$ 个专家”为简化概率模型，一个专家整批未被选中的概率是 $(1-K/E)^B$，因此

$$
\mathbb E[|U|]=E\left[1-\left(1-\frac KE\right)^B\right].
$$

这是分布假设下的期望，不是线上路由保证。它说明：每 token 只选少数专家，并不意味着一批 token 只访问少数专家。真实请求可能相关、偏向特定领域，连续批处理还会改变本轮 token 的组成，因而需要观察 $m_e$ 及其时间变化。

### 有效 FLOPs、补齐工作和权重读取

令 $P_e$ 为专家 $e$ 中线性投影的参数数，按一次乘加计两个 FLOPs，则这些投影的有效工作近似为

$$
F_{valid}\approx\sum_e 2P_e m_e.
$$

激活函数、Router、重排与共享路径尚未包含。若后端把每个专家行数补齐到粒度 $q_e$，且跳过空专家，可写成 $\widetilde m_e=q_e\lceil m_e/q_e\rceil$，实际投影工作近似为 $F_{exec}\approx\sum_e2P_e\widetilde m_e$。$F_{exec}/F_{valid}$ 描述这一种 padding 的工作放大；静态 capacity buffer、分块稀疏执行和不同 kernel 不必采用同一规则。[MegaBlocks](https://arxiv.org/abs/2211.15841)讨论了以块稀疏执行处理不均匀路由、减少 padding 或丢弃 token 的需求。不能把降低 capacity 后丢弃的工作当作无损加速。

再指定一个存储边界。若每个活跃专家的权重在该边界完整读取一次，令其权重字节为 $w_e$，本轮权重流量的参考值是

$$
V_{W,once}=\sum_{e\in U}w_e.
$$

这不是所有硬件上的 HBM 流量下界：跨轮缓存命中可能减少该边界的读取，tiling、缓存失效或多份物理副本可能增加读取。容量则要计所有驻留权重，不能只计 $U$。对近似相同的专家，$BK/|U|$ 表示每个活跃专家平均拿到多少分派，可作为权重复用的粗略信号；它掩盖了热点和小矩阵，不能替代完整的 $m_e$ 分布。

## 从专家分布到 rank 的完成时间

把逻辑专家 $e$ 放到物理位置 $r$ 后，以 $m_{er}$ 表示该副本接收的有效分派数。同一逻辑专家有多个副本时，应满足 $\sum_r m_{er}=m_e$；每次分派只由一份副本执行。TP 切分同一个专家的矩阵是另一维度，不能把各 shard 误计为独立副本。

```mermaid
flowchart LR
    R["逻辑路由：每 token 选哪些专家"] --> D["分布：专家行数与批内并集"]
    D --> P["放置与副本：分派到哪些 rank"]
    P --> W["实际工作：padding、权重读取、逐链路字节"]
    W --> C["依赖与争用：各 rank 完成、合并结果"]
    C --> O["反馈：期限、热点寿命、KV 余量"]
    O --> P
```

同样的 $BK$，分散路由可能访问更多专家权重、产生更多小矩阵；集中路由可能提高权重复用，却让某个 rank 或链路成为慢点。即使每专家行数相同，把几个热点放在同一 rank，也会改变该 rank 的累计工作。增加 EP 或复制热点专家会重新切分 $m_{er}$，但也可能降低单副本矩阵大小、增加活跃物理副本的权重读取，并改变跨节点流量。

所以先按放置方案计算每个 rank 的矩阵形状及每条实际路径的字节，再沿 dispatch、专家计算和 combine 的依赖求完成时间。需要共同进入下一层的执行组，受最晚就绪的必要结果限制；不能用平均专家时间，也不能只取最大的 $m_e$ 来代替。通信与计算的 overlap 还取决于是否竞争 HBM、SM 或相同链路。后文的 Roofline、分层 benchmark 与 overlap 指标分别检验这些环节；[推理部署与模型案例](<推理部署与模型案例.md>)讨论具体的副本与放置机制。

## 专家副本为什么会改变 KV 容量与排队

对每个 rank $r$，推理容量约束应在整个执行和迁移期间成立：

$$
M_{fixed,r}+\sum_{e\in\mathrm{resident}(r)}w_{er}
+M_{KV,r}(t)+M_{dispatch/workspace,r}(t)+M_{move,r}(t)
\leq M_r.
$$

$M_{fixed,r}$ 包含 dense／共享权重及其他静态对象，权重求和覆盖该 rank 所有部署层的驻留专家，$w_{er}$ 是本地专家副本或 shard 的实际存储。$M_{move,r}$ 只计尚未归入驻留集合的迁移暂存，避免重复计数。KV 应按本地物理页和实际复制方式计量；新旧权重同时存在时不能提前扣除旧副本。

热点副本占用的显存可能原本用于 KV。若它使可接纳请求减少、触发状态换出或使 batch 变小，专家层加速就未必改善端到端达标量。因此副本数与活跃请求数要共同选择，而不是先把专家负载摊平，再单独做 KV 规划。[vLLM 的 EP 部署文档](https://docs.vllm.ai/en/latest/serving/expert_parallel_deployment/)也明确提示 redundant experts 的内存代价，以及 KV 空间紧张时的取舍。此处的反馈关系与[批处理、排队与调度](<../../../05_Inference/21_批处理调度与排队.md#s1>)中的状态驻留和准入约束相连。

## 动态复制与迁移何时值得

路由热点是随时间变化的，当前最慢的专家不一定值得立即搬迁。先选定评价目标 $J$，例如固定请求集合的加权响应时间总和，或满足同一服务目标所需的资源成本。迁移方案与维持现状必须按相同质量、请求集合和时间范围比较；字节、延迟与费用不能直接相加。统计窗口结束时尚未完成的请求仍有剩余成本，不能靠将它们推迟到窗口外取得表面收益。

若以 $H$ 表示预计热点仍持续的时间，$s(t)$ 表示新放置在稳定运行时每单位时间节省的目标成本，那么一种回本判据是

$$
\int_0^H s(t)\,dt
> C_{move}+C_{switch}+C_{capacity}.
$$

右侧均换算为同一个 $J$ 的单位：$C_{move}$ 包含搬运暴露延迟及其资源争用，$C_{switch}$ 包含映射切换、排空或预热，$C_{capacity}$ 是额外权重及暂存挤占 KV 等空间带来的机会成本。这里左侧仅计未扣除这些代价的稳定收益；若端到端预测已包含某项，右侧不能再次扣除。该式是比较框架，不保证 $s(t)$ 恒定，也不把当前热点自动外推到整个 $H$。

异步迁移只可能隐藏部分关键路径时间，仍会使用链路、源端读取和目的端写入能力。热点寿命短于回本时间时，频繁追逐热点可能比保持原位更差；统计窗口、动作间隔和切换门槛需要同时考虑估计滞后与反复迁移。vLLM EPLB 的负载记录与周期性重平衡是这种在线控制的一种实现，并不意味着某个固定窗口适用于全部流量。

复制还必须保持模型语义：副本对应同一逻辑专家及权重版本，目标就绪后才能发布新映射，在途分派完成后才能回收旧位置。改变 Router 的 top-$K$ 或丢弃过载分派是模型行为变更，应另行验证质量。复制同一专家并重新分配其执行位置，才属于这里讨论的部署选择。

以上分析与[《深入理解 AI Infra》第 9 章的专家放置与复制](https://bojieli.github.io/ai-infra-book/manuscripts/09-%E5%88%86%E5%B8%83%E5%BC%8F%E6%8E%A8%E7%90%86.html)相衔接：逻辑激活量经过批内分布、物理放置和状态容量，才形成可用于部署选择的执行成本。下面的既有算例与观测指标用于检查这些环节。

## 一个完整的数值成本例子

假设：

- 每 rank 有 $T_r=4096$ tokens；
- Top-$K=8$；
- hidden size $d=7168$；
- dispatch 使用 FP8，$b=1$ byte；
- EP size $R=16$；
- 均匀 expert placement。

远程比例粗略：

```math
p_{remote}=1-\frac1{16}=0.9375.
```

单次 dispatch 主 activation byte：

```math
B_{dispatch}
\approx4096\times8\times7168\times1\times0.9375
\approx210\ \text{MiB}.
```

若 combine 使用 BF16：

```math
B_{combine}
\approx420\ \text{MiB}.
```

仅前向两次主 payload 已约：

```math
630\ \text{MiB/rank/layer},
```

还未计 metadata、scale、协议、padding 和 backward。

这个例子解释了为什么：

- Top-K 很大时 A2A 极重；
- FP8 dispatch 很有价值；
- combine 保持 BF16 会使反向流量更大；
- 必须依赖 overlap；
- 需要限制跨节点 fan-out；
- “只激活少量参数”没有直接消除 activation communication。

数字只是第一阶估算；真实系统可能在 EP 前先做 TP/SP、按节点聚合或使用 reduce-in-combine，需按实际 layout 修正。

## MoE 的 Roofline：训练与 decode 可能落在完全不同区域

GEMM 算术强度近似：

```math
AI=\frac{FLOPs}{Bytes\ moved}.
```

对 $[m,d]\times[d,n]$：

```math
F\approx2mdn.
```

当 $m$ 大，权重被很多 rows 复用，$AI$ 高，可能 compute-bound；当 $m$ 小，权重读入主导：

```math
AI\rightarrow O(m).
```

因此：

- training/prefill：更可能 compute-bound 或通信带宽受限；
- decode：更可能 weight-HBM-bandwidth、launch 和 network-latency 受限；
- Ultra-Sparse：即使总 FLOPs 更低，也更容易 memory-bound。

不要用 training grouped-GEMM TFLOPS 预测 decode TPOT。

## 如何正确 Benchmark 一个 MoE 系统


<a id="read-107"></a>


### 1 四层指标

#### Router 层

entropy（熵）按 H(p)=−∑pᵢlog pᵢ 衡量分布不确定性。分布集中时熵较低，分散时较高；熵本身不衡量回答正确性。

- Top-K latency；
- entropy；
- route churn；
- max/mean expert load；
- dead/overloaded experts；
- token drop rate。

#### Kernel 层

- permute/unpermute GB/s；
- Grouped GEMM TFLOPS；
- $m_e$ histogram；
- zero-token expert 数；
- launch 数；
- HBM/L2 hit；
- active warps/occupancy。

#### Communication 层

- dispatch/combine payload；
- effective bandwidth；
- P50/P95/P99 latency；
- intra-node / inter-node byte；
- per-rail utilization；
- SM used by comm；
- overlap efficiency。

#### End-to-end 层

MFU（Model FLOPs Utilization，模型浮点运算利用率）通常按“模型约定的每步 FLOPs ÷ 步耗时 ÷ 全部设备的对应精度峰值”计算。重计算通常不计入模型有效工作量，比较前必须固定 FLOPs 与峰值口径。

- tokens/s/GPU；
- step time；
- MFU；
- TTFT/TPOT；
- request P99；
- memory peak；
- cost per million tokens。


<a id="read-108"></a>


### 2 必须使用真实 route trace

均匀随机路由只适合测理想上界。至少准备：

1. perfectly balanced；
2. 真实训练 trace；
3. 代码/中文等单领域 trace；
4. hot-expert stress；
5. 0-token experts；
6. 路由突然漂移；
7. prefill 与 decode 两套 token counts。

DeepSeek 公开 profile 特别说明使用绝对均衡路由模拟，因此读 trace 时不能把理想 overlap 直接当作线上负载结论。

## 如何测 Communication–Computation Overlap

只看 profiler 上红色通信 kernel 与 GEMM 重叠还不够。建议计算：

```math
\eta_{overlap}
=\frac{T_{comm}+T_{compute}-T_{joint}}
{\min(T_{comm},T_{compute})}.
```

其中：

- $T_{comm}$：通信单独运行；
- $T_{compute}$：计算单独运行；
- $T_{joint}$：共同运行。

理想情况下 $\eta_{overlap}\approx1$。

但还要观察共同运行后：

- GEMM 是否变慢；
- 通信有效带宽是否下降；
- HBM bandwidth 是否饱和；
- SM 分配是否合适；
- PP bubble 是否变化；
- P99 是否因偶发 imbalance 变差。

“时间线上重叠”不等于“通信被免费隐藏”。

## 常见故障排查


<a id="read-111"></a>


### 1 loss 正常，但 step time 周期性尖峰

检查：

- per-layer max/mean expert load；
- 某领域 batch 是否形成热专家；
- EPLB/placement 更新周期；
- IB congestion、adaptive routing、rail imbalance；
- allocator 是否因动态 buffer 扩容同步；
- checkpoint/日志是否与网络争用。


<a id="read-112"></a>


### 2 某些 ranks OOM，其他 ranks 显存充足

检查：

- recv assignments 与 intermediate activation；
- capacity 是否按平均而非 max 估计；
- backward saved activation 是否 dropless；
- redundant experts 是否在同 rank 过多；
- Grouped GEMM workspace 是否随最大 expert shape 分配；
- activation offload 与 EP traffic 是否互相堵塞。


<a id="read-113"></a>


### 3 MFU 很低，但网络利用率也不高

可能不是带宽瓶颈，而是：

- messages 太小，RTT/launch 主导；
- host 在读取 counts 后同步；
- permute kernel 慢；
- Grouped GEMM $M$ 太小；
- CUDA Graph 未生效；
- 0-token expert 导致分支或 launch 浪费；
- collective 次序有 barrier。


<a id="read-114"></a>


### 4 Grouped GEMM 不如 for-loop

检查：

- 是否只有少量大 experts；
- grouped kernel tile 是否适合当前 $M$ 分布；
- pointer/offset metadata 是否每次 CPU 构造；
- autotune 是否包括 warmup；
- weight layout/transpose 是否额外 copy；
- FP8 quantization 是否单独产生多个 kernel；
- GPU 架构是否属于优化路径；
- 比较是否包含相同 activation/fusion。


<a id="read-115"></a>


### 5 Router collapse

检查：

- load histogram、entropy、top1 share；
- balance coefficient；
- aux-free bias update speed；
- Router logits scale/z-loss；
- 数据顺序是否长时间单领域；
- dead expert 初始化；
- global-batch statistics 是否正确跨 DP 汇总。


<a id="read-116"></a>


### 6 多节点 hang

检查：

- 所有 ranks 的 send/recv count 总和是否匹配；
- process group 建立顺序；
- EP/TP/DP group 是否一致；
- 某 rank 是否在 OOM 后未进入 collective；
- CUDA stream event 依赖是否形成环；
- varlen/empty expert 是否跳过了必须参与的 collective；
- NCCL/RDMA timeout 前的第一处 rank divergence。


<a id="read-117"></a>


### 7 训练均衡，线上 P99 仍很差

检查：

- 线上领域分布与训练分布差异；
- expert placement 是否按在线 $\lambda_e$；
- hot expert 是否需要副本；
- request-level batching 是否把同类流量集中；
- decode batch 是否太小；
- EPLB weight migration 是否阻塞请求；
- 单 expert 的量化/kernel 路径是否不同。

## MoE 训练的五组相容条件


<a id="read-120"></a>

### 模型侧

模型身份由 $E,K,d,d_e$、shared expert 数量、MoE layer frequency 与 dense warmup layers 共同定义。Router 的 softmax/sigmoid、normalization 与 precision 改变打分语义；balance、z-loss、capacity/drop 和 node/group-limited 策略分别约束分布、数值与可达专家。因此 total parameters 与 active parameters 必须区分：前者决定需要存储的状态，后者只描述当前激活路径。


<a id="read-121"></a>

### 并行侧

EP/TP/DP/PP/CP process groups 与每 GPU 的 expert ownership 定义状态归属。同一 expert 的 DP gradient group 必须聚合相同参数的贡献；empty expert 和非整除专家数也不能破坏通信顺序。checkpoint 在不同 EP size 下恢复，则进一步要求按专家身份重分片，而不是按旧 rank 号直接加载。


<a id="read-122"></a>

### Kernel 侧

真实 $m_e$ 分布决定专家矩阵形状，因此 forward、dgrad 与 wgrad 不能共用一个笼统的 GEMM 性能结论。端到端成本还包括 permute/unpermute，BF16/FP8/FP4 分别有 shape 与 alignment 约束。Grouped GEMM、循环调用与 multi-stream 的优劣取决于这些形状和 launch 成本；CUDA Graph/compile 的多次 replay 还要求动态输入和状态被正确更新。


<a id="read-123"></a>

### 通信侧

通信账本要区分节点内与跨节点字节。预分配 send/recv buffer 改变分配成本，throughput 与 low-latency protocol 面向不同消息形态，通信 SM 配额又与计算争用资源。overlap 的收益取决于 joint time，而非两段各自耗时之和；NIC rail、VL/QoS 和拥塞决定理想账本在物理网络上如何兑现。


<a id="read-124"></a>

### 稳定性侧

训练早期的 Router imbalance、单领域 batch 与路由热点会放大瞬时负载，因而 max buffer headroom 需要覆盖非平均情况。loss spike、router entropy 和 dead expert 是不同失效信号；checkpoint 恢复还必须保持 routing 与 optimizer state 一致，权重能够加载并不足以证明轨迹接续正确。

---


<a id="read-125"></a>


## MoE 服务的容量与动态状态

服务部署首先受 HBM 总容量约束：权重、KV Cache、workspace 和 redundant experts 必须同时容纳。prefill/decode 的 EP/TP/DP 选择取决于各自 batch 形态，continuous batching 下实际 $m_e$ 分布会随着请求变化。EPLB 的 window、interval、replica 数与迁移策略共同决定对热专家、领域漂移和突发流量的响应；质量与容量因此需要结合 P50/P95/P99 TTFT/TPOT 理解。

低 batch decode 往往更关心 low-latency dispatch；CUDA Graph 还要容纳动态 offsets 与 empty experts。量化依赖质量和 kernel coverage，CPU offload 依赖 PCIe stall 与 cache hit。故障 rank、网络抖动和 expert migration 的可观测性决定尾延迟能否归因。成本比较最终落在最小部署单元，而不是仅按 active parameters 推算。

## 常见误区


<a id="read-127"></a>

### 误区 1：MoE 只有 active parameters 需要放显存

错误。所有本地 expert weights 都必须驻留或被按需搬运；total parameters 决定集群最小存储规模。


<a id="read-128"></a>

### 误区 2：MoE FLOPs 是 Dense 的 $K/E$

只对 expert bank 的理想计算近似成立，还需加入 shared/dense paths、Router、通信、padding 和 kernel 低利用率。


<a id="read-129"></a>

### 误区 3：负载均衡就是每 expert token 数相同

系统真正受 rank makespan、跨节点流量、rank 内 GEMM schedule 和在线 placement 共同影响。


<a id="read-130"></a>

### 误区 4：All-to-All 只取决于网络带宽

小消息 RTT、metadata、permute、SM 占用、拓扑和拥塞都可能主导。


<a id="read-131"></a>

### 误区 5：Grouped GEMM 一定优于多个 GEMM

少量大 experts、错误 tile 或不成熟 backend 下可能相反，必须按真实 shape 测量。


<a id="read-132"></a>

### 误区 6：训练时平衡，Serving 就平衡

线上流量分布不同，需要 placement、replica 和 EPLB。


<a id="read-133"></a>

### 误区 7：更大的 EP 一定更快

EP 越大，每 GPU 权重越少，但 remote ratio、部署规模和通信参与者越多，expert batch 也可能更小。


<a id="read-134"></a>

### 误区 8：DualPipe 是通用最优流水

Kimi K2 的公开选择已说明，内存和模型 shape 不同时，interleaved 1F1B + 小 EP 可能更合适。


<a id="read-135"></a>

### 误区 9：只优化 Expert GEMM 就够了

在 Ultra-Sparse 模型中，permute、dispatch、combine、weight load 和 host scheduling 常占更大比例。

## Dense 还是 MoE？从 Hardware Envelope 选择


<a id="read-137"></a>

### 更适合 MoE

- 大规模训练集群；
- 总容量是能力瓶颈；
- 有高带宽 GPU 互联；
- batch 足以形成可用 expert GEMM；
- Serving 能承担 EP 最小部署单元；
- 有专用 kernel/communication/runtime 团队；
- 希望 active compute 远小于 total capacity。


<a id="read-138"></a>

### 更适合 Dense

- 单机或小集群；
- 低 batch、低并发；
- 网络慢或无 NVLink；
- 权重必须完整本地驻留；
- 追求简单故障恢复和部署；
- active parameter 规模本身不大；
- 规则大 GEMM 更容易达到高利用率。

未来不是 Dense 被 MoE 淘汰，而是架构按部署边界分化：

```math
\text{Cloud frontier}\rightarrow\text{Ultra-Sparse MoE},
```

```math
\text{Local / edge / low-batch}\rightarrow\text{Dense or compressed MoE}.
```

## 一条推荐的 MoE Infra 学习路径

1. **Dense SwiGLU FFN**：参数、FLOPs、GEMM shape；
2. **Router + Top-K**：token-choice 与 load metrics；
3. **Permutation**：count、prefix sum、scatter/gather；
4. **Expert Parallel**：dispatch/combine 与 process groups；
5. **Grouped GEMM**：ragged $M$ 与 tile scheduler；
6. **Load balancing**：aux loss、bias、QB、EPLB；
7. **Network topology**：NVLink/NVSwitch、PCIe、IB/RoCE、RDMA；
8. **Overlap**：CUDA streams、SM partition、PP schedule；
9. **Serving**：prefill/decode、redundancy、CUDA Graph；
10. **Low precision**：FP8/FP4、scale layout 与 communication compression；
11. **现代案例**：DeepSeek、Kimi、Qwen、GLM；
12. **Profiler**：从理想 balanced trace 走到真实 route trace。

学一个 Grouped GEMM kernel 时，应始终向上追问：

```math
\text{Ultra-Sparse MoE}
\rightarrow
\text{token fragmentation}
\rightarrow
\text{many ragged GEMMs}
\rightarrow
\text{Grouped GEMM scheduler}.
```

这样 kernel 才会被放回完整系统中理解。

<a id="read-140"></a>


## 最终心智模型

MoE 的四层本质：

1. **算法层**：Router 为 token 选择条件参数；
2. **张量层**：token 被复制、重排、按 expert 聚合；
3. **分布式层**：EP 用 All-to-All 把 token 送到权重所在处；
4. **硬件层**：许多 ragged small GEMMs 与网络争用 SM、HBM 和互联。

完整瓶颈迁移链：

```math
\text{Dense FFN FLOPs}
\rightarrow
\text{Sparse active experts}
\rightarrow
\text{A2A + load imbalance}
\rightarrow
\text{small Grouped GEMM}
\rightarrow
\text{weight bandwidth + placement}
\rightarrow
\text{low precision + redundancy + overlap}.
```

如果只记住八句话：

1. Total parameters 决定容量和存储；activated parameters 只近似决定每 token 计算。
2. Top-K 同时放大 Expert FLOPs、token assignments 和通信量。
3. 最慢 rank 决定整层时间，所以 max load 比平均 load 更重要。
4. EP 节省每 GPU expert weight，却引入 dispatch/combine All-to-All。
5. Grouped GEMM 是 many-ragged-GEMM 的调度抽象，不是一个永远最快的固定 kernel。
6. Training/prefill 更关注吞吐和带宽；decode 更关注权重读取、小消息与 P99。
7. Router balance、expert placement、replica selection 是三个不同层次。
8. DeepEP、DualPipe、MoonEP、FP8/FP4 不是外围优化，而是 Ultra-Sparse MoE 能扩展的组成部分。
