# Omni 性能与质量评估

[训练篇](<../training/Omni训练与后训练.md>)区分了多个任务目标，评估也应保留这些边界。一次语音请求可以内容正确但首音频太慢，也可以响应很快却反复断流。把它们压成单一 tokens/s，会遗漏主要问题。

## 首先固定测量边界

案例 A 从用户说话结束，到服务器输出首块波形是 160 ms，到客户端收到是 180 ms，到真正播放是 220 ms。这是[流式篇](<../serving/Omni流式生成与会话状态.md>)的教学预算。每个指标应同时写出起点、终点、采集位置与是否含排队；“首音频延迟”单独一个名字不够。

| 指标 | 可操作的定义 | 配套检查 |
|---|---|---|
| 首可播放音频延迟 | 输入结束或请求开始 → 设备开始播放 | 起点口径、初始缓冲、输入上传与 endpoint 判定 |
| 播放缺口 | 应连续播放期间，没有可播放样本的区间 | 总时长、次数、最大缺口，区分用户主动暂停 |
| RTF | 指定合成区间耗时 / 生成音频时长 | 是否含排队、设备数、并发与流式分块 |
| 打断停止延迟 | 用户开始打断 → 旧音频实际停止 | 误打断、漏打断、停止后旧块是否复活 |
| 音视频偏移 | 对应视觉/声音事件在共同时间轴上的偏差 | 输入自身偏移与生成/播放引入的偏移分别查 |
| 媒体完成延迟 | 请求开始 → 合格最终媒体可见 | 预览、最终结果、传输与解码分别标记 |

Endpoint detection 是判断用户这一轮是否说完。判得太晚增加等待，判得太早截断输入；固定输入文件结束时刻的压测通常绕过了这一步，不能直接代表真实对话体验。

## 用时间线检查平均值的盲区

四个 200 ms 音频块在 `[180,340,680,770]` ms 到达，220 ms 开始播放，产生一个 60 ms 缺口。若以“首次播放到最后结束”为分母，缺口占比是 `60/860≈6.98%`；若分母用有效音频时长，则为 `60/800=7.5%`。两者都能定义，但报告必须说明分母。

RTF=0.75 只说明指定区间生产 800 ms 音频用了 600 ms。它不约束最慢块、网络抖动和客户端排队，也不等于每个并发用户都有 25% 余量。应把阶段队列、chunk 到达、播放游标画在同一条请求时间线上。

同时记录 p50、p95、p99 与样本数；少量请求无法稳定估计高分位。超时请求不能从延迟统计和总体成功率中悄悄消失。[实验统计](<../../07_Practice/29_性能测量与因果分析.md#s3>)讨论区间与删失，[排队与容量](<../../05_Inference/21_批处理调度与排队.md#s2>)讨论开环/闭环负载。

## 质量要沿任务拆开

音频理解需要检查转写、非语言声音、内容问答和时间定位。词错误率 WER 定义为 `(替换 S + 删除 D + 插入 I) / 参考词数 N`。10 个参考词中替换 1 个、漏掉 1 个、无插入，则 WER=20%；如果遗漏的是“不要”之类的否定词，语义损害可能远大于普通词。中文还需固定按字或何种分词口径统计。

语音输出应分别检查说了什么和说得怎样：可懂度、发音、音色一致、韵律、噪声、块边界接缝。MOS（平均主观评分）是评审者按明确量表给分再平均；要报告听评条件、人数、样本覆盖和不确定性，不能把模型自动评分直接命名为人工 MOS。

图像/视频生成要检查条件遵循、参考一致性、局部伪影与时间连续性。只观察最终图像清晰不代表遵循了文字要求；视频逐帧清晰也不代表运动合理。自动指标用于规模化筛查，人工和具体任务验收用于发现指标盲区。

交互任务还应检查对话状态：已播放前缀是否被正确记住、打断后是否重复播报、旧回答是否泄漏进新回答、附和是否被误判成取消。这里的正确性依赖客户端协议与服务状态，不能只跑离线模型分数。

## 定义满足约束的有效吞吐

Goodput 指单位时间内同时满足任务质量与服务约束的有效完成量。假设一个 10 秒窗口中有 100 个请求到达，80 个最终完成，其中只有 60 个同时满足质量、首音频和最大播放缺口要求。以到达请求为分母的成功率是 60%，这段窗口内若这些合格请求均完成，则 goodput 是 6 请求/秒。只报告 `60/80=75%` 会隐藏未完成的 20 个请求。

实际评估还需说明观察窗口与排空规则：窗口结束仍在途的请求单列，不随意当作成功或失败。请求数也不足以比较不同负载，可同时给出合格音频秒数/秒、每分钟合格音频成本、合格图像数/设备小时，并固定内容长度与质量门槛。

## 一张可复现的实验记录

| 类别 | 至少记录 |
|---|---|
| 模型与实现 | 权重 revision、运行时 commit、codec/解码器版本、adapter、精度 |
| 媒体输入 | 时长、采样率、声道、分辨率、帧率、抽帧/裁剪、语言与说话人覆盖 |
| 生成配置 | 输出长度/分辨率、步数、种子、求解器、引导强度、chunk 大小与 lookahead |
| 服务负载 | 到达分布、并发、设备布局、队列上限、超时、缓存冷热 |
| 客户端 | 网络条件、缓冲策略、采集/播放设备、实际播放和打断事件 |
| 结果 | 完成/失败/取消/在途数、质量指标、时延分布、原始逐请求时间线 |

比较两种优化时，优先对相同输入配对，固定可控随机性，并保留没有成功生成的样本。随机种子相同不保证跨 kernel 或并行布局逐位相同；因此同时检查数值偏差与任务质量，不把“不同”自动当作“变差”。

## 最小验证阶梯

先用[标准库脚本](<../../examples/omni_walkthroughs.py>)核对公式和状态，再用真实模型离线检查固定输入的输出与分块拼接；随后单会话记录采集到播放的完整链路，再做负载压测、网络扰动和中途取消。每层解决不同问题，不能用前一层通过替代后一层证据。

当前本支线完成的是数学和协议模拟、固定源码静态检查，没有运行语音模型、图像模型、GPU 压测或真人听评。因此正文给出的是可验证的方法与教学答案，不声称达到任何实测延迟或质量门槛。

## 自测

**改小 chunk 后首音频更快，就能宣布优化成功吗？** 还要检查调用开销、播放缺口、音质、吞吐和打断尾部，固定质量门槛后比较。

**只在成功请求中计算 p99，有什么风险？** 大量最慢请求可能已超时退出，剩余分位数看起来反而更好；应同时呈现失败和在途边界。

有了这些测量定义，才可以判断[并行与执行优化](<../parallelism/Omni并行与执行优化.md>)是否改善了用户真正关心的结果。
